第 8 章我们看了上下文工程的全景——其中 `transformContext` 只是低层 Agent 的扩展点；coding-agent 的自动 Compaction 则由 `AgentSession` 调度。当当前会话上下文逼近模型窗口，或模型明确报告输入溢出时，coding-agent 才进入相应压缩路径。

这一章沿源码看 `AgentSession` 如何结合 usage、估算和 overflow 错误检查压缩条件，如何选择保留区、生成摘要，以及什么时候会做一次受限的 overflow recovery。低层 `Agent` 本身不会自动压缩。

## 一、问题：对话越来越长，窗口装不下了

Agent 和 LLM 的对话是"有状态的"——后续请求会带上当前上下文。工具结果、长代码和多轮消息都可能让输入逐步接近模型上下文窗口。下面的 185K / 200K 数字只是帮助理解压缩收益的示意，不代表某个模型固定的窗口或真实会话统计。

<Diagram file="/assets/260702-ch09-before-after.svg" caption="压缩前后 Token 占用对比" id="260702-ch09-before-after" />

**配图说明**：左侧红色条带——185K token 几乎塞满 200K 窗口。右侧绿色——压缩后只剩 60K（10K 摘要 + 50K 近期消息），腾出 140K 可继续聊。底部说明压缩是有损的但保留了目标/约束/决策等结构化信息。

满了会怎样取决于 provider：有的返回可识别的错误，有的可能成功响应但报告的 input 超窗，还有的会以 length stop 且零输出等信号表现。错误检测有明确条件，不是所有 provider 都能无误识别。

最直觉的解决方案是删旧消息——把前 30 轮扔掉，只保留最近 20 轮。但这样 Agent 就"失忆"了——它不记得你最初让它做什么、不记得之前做了什么决策、不记得改了哪些文件。

Pi 的解法是**压缩（Compaction）**：把旧消息变成一段结构化摘要，用摘要替代原始消息。这样既腾出了空间，又保留了关键信息。

```
压缩前（185,000 token）：
┌── 第1-30轮（135,000 token）──┬── 第31-50轮（50,000 token）──┐
│  原始消息（大量工具结果）      │  原始消息（最近的上下文）      │
└──────────────────────────┴──────────────────────────┘

压缩后（约 60,000 token）：
┌── 摘要（约 10,000 token）──┬── 第31-50轮（50,000 token）──┐
│  结构化总结（目标、进度、     │  原始消息（完整保留）          │
│  决策、文件跟踪……）          │                              │
└────────────────────────┴──────────────────────────┘
```

Agent 仍然"记得"前 30 轮做了什么——只是记忆从"原始录像"变成了"摘要笔记"。

### 一个关键时序：压缩发生在两轮对话之间

在读后面所有细节之前，先把一条核心时序刻在脑子里——**压缩不是在对话进行中触发的，而是在两轮对话之间发生的**：

```
用户问 → Agent 回答 → (Agent 这一轮结束，发 agent_end 事件)
                              │
                              ▼
                     检查 token：超阈值了吗？
                              │
                   ┌──────────┴──────────┐
                   ▼                     ▼
                没超 → 等下一轮       超了 → 立刻压缩
                                       ├─ 找切割点
                                       ├─ 生成摘要
                                       └─ 把 CompactionEntry 写进 Session Tree
                                              │
                                              ▼
                              下一轮用户开始问时：
                              buildSessionContext() 从 Session Tree 重建上下文
                              → CompactionSummaryMessage 替代旧消息
                              → LLM 看到的是"摘要 + 近期消息"
```

**这是理解常规阈值压缩的主线**，但不是唯一入口。`AgentSession` 在 `agent_end` 后检查阈值；发送下一条 prompt 前也会补查上一次响应，用来处理 aborted 或没有有效 usage 的情形。遇到 overflow / recoverable length stop 时，压缩与是否继续当前 turn 还取决于响应终态，后文会单独区分。

## 二、什么时候压缩：红灯亮起

### 触发条件

阈值压缩由 `shouldCompact` 判断：

```typescript
function shouldCompact(contextTokens, contextWindow, settings): boolean {
    if (!settings.enabled) return false;
    return contextTokens > contextWindow - settings.reserveTokens;
}
```

默认设置为 `enabled = true`、`reserveTokens = 16,384`、`keepRecentTokens = 20,000`。如果某个模型窗口是 200,000 token，按默认 reserve 算出的示例阈值是 183,616；真实阈值取决于当前模型的 `contextWindow` 和设置。

当 `contextTokens` 严格大于 `contextWindow - reserveTokens` 时，才触发压缩。

`reserveTokens` 为后续生成和压缩操作留出空间。token 数恰好等于 `contextWindow - reserveTokens` 时，这个函数还不会触发。

### Token 估算：不精确但够用

一个关键问题：怎么知道当前有多少 token？coding-agent 优先使用有效 assistant 响应的 provider usage。需要估算时，`estimateContextTokens` 会用最后一条有效 usage 作为基数，再估算它之后追加的消息；如果找不到有效 usage，才估算全部消息。中止、错误和全零 usage 不会作为有效基数。单条消息估算使用 `ceil(chars / 4)` 启发式；图片按固定字符估值计入。它不是 tokenizer 结果，也不保证对不同语言、内容类型或 provider 同样准确。

`calculateContextTokens` 优先读 usage 的 `totalTokens`，没有可用总数时再把 `input`、`output`、`cacheRead`、`cacheWrite` 相加。压缩后，coding-agent 的 `getContextUsage()` 在拿到压缩后新一条有效响应 usage 前会把 token 数报告为未知；不能把最近一条保留 assistant 的旧 usage 当成压缩后上下文的精确计数。

```typescript
// 单条消息的 fallback estimate：按角色提取文本、thinking、工具调用等内容
function estimateTokens(message: AgentMessage): number {
    let chars = 0;
    // ...按 message.role 分别累加 text/thinking/toolCall/command/output/summary 的字符数
    return Math.ceil(chars / 4);  // chars / 4
}
```

因此 `chars / 4` 只作为缺少有效 usage 时的 fallback。它能让压缩逻辑继续工作，但不应把估算值当作精确 token 计数，也不能据此推出特定语言下的固定误差方向。

### 两种触发场景

| 场景 | 什么时候触发 | 意味着什么 |
|------|------------|-----------|
| **阈值压缩** | usage 或 fallback 估算超过 `contextWindow - reserveTokens` | 压缩已完成的上下文；不重试已完成响应 |
| **overflow recovery** | 当前模型的响应命中 overflow 条件，或是可恢复的 length stop | 移除失败 / 截断 assistant 消息，压缩，再至多继续一次 |

阈值压缩与 overflow recovery 是两个分支。后者的检查还会考虑模型是否与当前会话模型一致，避免旧模型的失败响应触发新模型的恢复流程。

`isContextOverflow` 有三类信号：① `stopReason === "error"` 且错误文本匹配 provider overflow 模式，并排除限流等已知非溢出错误；② 响应正常结束，但 `usage.input + usage.cacheRead > contextWindow`；③ `stopReason === "length"`、`usage.output === 0`，并且输入与 cacheRead 至少占窗口的 99%。**零输出本身不代表 overflow。** 另一个独立信号 `isRecoverableLength` 要求 stop reason 是 `length`、目标输出上限大于 0，且实际输出小于该目标；它覆盖模型 / provider 提前截断的恢复场景，不等同于 `isContextOverflow`。

## 三、在哪切：切割点算法

知道该压缩了，但从哪里"下刀"？不能随便切——有些位置切了会破坏数据完整性。

<Diagram file="/assets/260702-ch09-cut-point.svg" caption="压缩的切割点算法" id="260702-ch09-cut-point" />

**配图说明**：示意路径从最新 entry 向旧 entry 累积估算 token。`toolResult` 不是切点；上下文可见的 user-like 消息、assistant 消息可作为候选。切在 assistant 上时，切点所在 turn 的前缀会被单独摘要，切点及其后缀保留。

### 不是哪里都能切

LLM 的对话历史有严格的结构约束。比如 `ToolResult` 消息必须紧跟在触发它的 `AssistantMessage`（含 ToolCall）之后。如果你把 ToolCall 留在"保留区"、把 ToolResult 切到"压缩区"，模型会看到"我调用了 read 工具，但结果在哪？"——上下文断裂。

因此切割点必须是**上下文可见的合法 entry**：`toolResult` 不可选为切点，避免把 assistant 工具调用留在压缩区、却把它的结果单独放进保留区。当前实现还允许 assistant 和 user-like 消息作为候选；user-like 包括普通 user、`bashExecution`、`custom`、`branchSummary` 和 `compactionSummary`。

```
entry:  0     1     2      3       4     5      6       7      8
       ┌─────┬─────┬──────┬───────┬─────┬──────┬───────┬──────┬─────┐
       │ hdr │ usr │ ass  │ tool  │ usr │ ass  │ tool  │ ass  │tool │
       └─────┴─────┴──────┴───────┴─────┴──────┴───────┴──────┴─────┘

有效切割点 = [1(usr), 2(ass), 4(usr), 5(ass), 7(ass)]
                                                       ↑
                                          toolResult 不能作为切点
```

`findValidCutPoints` 的规则是：**上下文可见的 user-like / assistant entry 可以作为候选，`toolResult` 不是候选**。注释里的关键说明是：

> When we cut at an assistant message with tool calls, its tool results follow it and will be kept.

### 切点的语义：保留区的起点

理解切割点要抓住一个关键——**切点不是"被切掉的最后一条"，而是"保留区的第一条"**。`prepareCompaction` 会先把可压缩范围限定在上次 compaction 边界之后；选出的 entry id 会写进新 `CompactionEntry.firstKeptEntryId`。

切点 = user，意味着什么？user 自己进保留区，**它后面的 assistant 和 toolResult 也都跟着进保留区**——这个 user 开头的完整 Turn 全部保留。被压缩的是 user **之前**的消息。

```
例子：切点选 entry 4 (usr)
entry:  0     1     2      3       4     5      6       7      8
       hdr   usr   ass   tool    [usr]  ass   tool    ass   tool
       └──────── 压缩区 ────────┘  └────── 保留区 ──────────────┘
                                   ↑
                              切点 = 保留区第一条
                              user + 后面的 ass + tool 全部保留
                              → 这个 Turn 完整！
```

所以在 user-like turn 起点切，通常能保留一个完整 turn；assistant 切点则可能需要单独处理 turn 前缀。

### 向后遍历：保护最重要的东西

确定有效切割点后，从哪里切？Pi 的策略是**从后往前累积**：

```
从最新消息往回走，累积 token 数。
当累积量 >= keepRecentTokens（20,000）时，停止。
在达到预算的位置或其后，找最近的有效切割点——它成为保留区的起点。
```

为什么从后往前？因为**最近的上下文最重要**。模型需要知道"刚才做了什么""刚才读了什么文件""用户最新说了什么"。往回走直到累积够 20,000 token，确保保留足够的近期上下文。

```typescript
function chooseCutPoint(
    cutPoints: number[],
    startIndex: number,
    endIndex: number,
    keepRecentTokens: number,
    estimateEntryTokens: (index: number) => number,
) {
    let accumulatedTokens = 0;
    let cutIndex = cutPoints[0];

    for (let i = endIndex - 1; i >= startIndex; i--) {
        accumulatedTokens += estimateEntryTokens(i);
        if (accumulatedTokens >= keepRecentTokens) {
            cutIndex = cutPoints.find((candidate) => candidate >= i) ?? cutPoints[0];
            break;
        }
    }

    return cutIndex;
}
```

这段是便于看清选择规则的有效 TypeScript 节选；真实 `findCutPoint` 还会从 session entry 转成上下文消息后估 token，并把 `CompactionEntry` 当作边界处理。

切割结果把消息分成两组：

```
切割点之前的消息 → messagesToSummarize（被压缩）
切割点之后的消息 → kept（保留）
```

## 四、切掉的部分怎么处理：结构化摘要

被压缩的那几十轮对话，不是直接扔掉，而是变成一段**结构化摘要**。

### 摘要的格式：不是自由文本，是填表

Pi 不是让 LLM "随便写一段总结"，而是要求它填一个固定格式的表格——6 个 section：

```
## Goal                    ← 用户最初要做什么
## Constraints & Preferences  ← 有什么约束
## Progress                ← 做了什么（Done / In Progress / Blocked）
## Key Decisions           ← 关键决策
## Next Steps              ← 下一步做什么
## Critical Context        ← 不能忘记的关键信息
```

为什么用结构化格式？因为自由文本容易遗漏信息——LLM 可能花大篇幅描述某个有趣的技术细节，却忘了记录用户的核心需求。固定 section 强制 LLM 覆盖每个维度，减少遗漏。

### 摘要生成：一次或两次 LLM 调用

生成摘要的过程是：先把消息序列化成文本，然后调用 LLM 生成摘要。

```
原始消息（AgentMessage[]）
    │
    ▼ 序列化
"[User]: 帮我修 auth.ts
 [Assistant tool calls]: read(path=\"auth.ts\")
 [Tool result]: export function authenticate() {...}
 [Assistant]: 找到问题了，缺少 salt..."
    │
    ▼ LLM 调用（用摘要 prompt）
    │
结构化摘要
    ## Goal
    Fix authentication bug in auth.ts
    ## Progress
    ### Done
    - [x] Read auth.ts, identified missing salt
    ...
```

正常压缩用一次摘要调用；如果切点拆开一个 turn，则先生成历史摘要（存在待摘要历史时），再顺序生成一个更短的 turn-prefix 摘要，最后合并。进入摘要 prompt 前，消息会先转成 LLM 标准消息并序列化为带角色标签的文本；每条 tool result 在序列化摘要输入里最多保留 2000 个字符，避免原始工具输出再次把摘要请求撑大。摘要调用不提供工具，响应若以 `length` 截断、报错或试图调用工具，都不会作为成功摘要持久化。

### 增量更新：不是每次从零开始

如果一个长对话被压缩了多次（第一次压缩第 1-30 轮，第二次压缩第 31-50 轮），第二次压缩时会传入上一次的摘要作为 `previousSummary`：

```
第一次压缩：
  输入：第1-30轮原始消息
  输出：摘要 A

第二次压缩：
  输入：摘要 A + 第31-50轮原始消息
  输出：摘要 B（在 A 的基础上合并新信息）
```

提示词要求 LLM **更新而非从零开始**——保留已有信息、加入新进度，并在状态变化时调整下一步；不再相关的信息允许移除。这是 prompt 对摘要结构的约束，不代表模型每次都会逐条无损保留。

### 文件跟踪：压缩不只是摘要文字

对于编码 Agent 来说，"改了哪些文件"是至关重要的信息。Pi 的摘要里还维护一个文件跟踪列表：

```
<read-files>
src/utils/hash.ts
</read-files>

<modified-files>
src/auth.ts
</modified-files>
```

这些列表跨压缩累积——准备下一次压缩时，coding-agent 会从上一条由 Pi 生成的 CompactionEntry.details 取回文件集合，再加入这次被摘要消息中的工具调用。`readFiles` 只保留读过但没有写入或编辑过的文件；写过 / 编辑过的文件进入 `modifiedFiles`，两组不会重复列出同一个已修改文件。

## 五、极端情况：Turn 分割

§三 讲了多种上下文可见消息都能成为候选切点。turn 起点与普通 assistant 切点的性质不同——

- **turn-start 切点**：包括 user、bashExecution、custom、branchSummary、compactionSummary；作为 turn 起点时不会拆分此前的 turn
- **assistant 切点**：如果向前能找到 turn 起点，就会**切断 Turn**；前缀单独生成摘要，选中切点及其后续消息留在上下文里

`findCutPoint` 最后通过 turn-start 判定是否需要拆分：

```typescript
const startsTurn = isTurnStartEntry(cutEntry);
const turnStartIndex = startsTurn ? -1 : findTurnStartIndex(entries, cutIndex, startIndex);
const result = {
    turnStartIndex,
    isSplitTurn: !startsTurn && turnStartIndex !== -1,
};
```

**切点是 turn-start entry → 不会标记为 split turn**。**切点是 assistant → 如果向前找到 turn 起点就标记 split turn**。实现会把 turn 起点到切点前的可见消息作为 `turnPrefixMessages`，单独处理。

### 为什么允许 assistant 切点？

最直觉的疑问是：既然 assistant 切点会切断 Turn，为什么不允许只切 user？这样不就完全避免 split turn 了吗？

从实现可以确认：候选切点包含 assistant 消息，切在 turn 中间时会额外准备 turn-prefix 摘要。一个合理的设计动机是：只允许 turn-start 切点，可能为了保住最近一轮而把更早的消息也留在保留区；允许 assistant 切点能提供更细的保留边界。这个动机是根据算法结构作出的解释，不是源码测得的压缩收益。

看这个示意场景：

```
entry:  1     2      3      4      5     6      7     8
       usr   ass   tool   ass   tool   ass   tool   ass
                                          ↑
                                    向后累积到这里 token 预算用完
```

假设向后累积到 entry 6 时累积量达到 `keepRecentTokens`。这时实现会在当前位置或之后寻找最近的合法候选：

- 如果只允许 turn-start 切点，最近的 turn-start 可能很早，保留区会包含更多消息。
- 允许 assistant 切点时，可以选中更靠近 token 边界的 entry；若该 assistant 不在 turn 起点，则用 turn-prefix 摘要保留它前面的必要上下文。

这是**切点粒度与 turn 完整性之间的权衡**：更细的候选边界可能减小保留区，但会拆分 turn，因此代码用单独的摘要保存 turn 起点到切点前的前缀。是否在特定对话里减少了多少 token，需要实际测量，不能从这段算法直接推出。

### turnPrefix 机制：被切断的 Turn 怎么办？

```
entry:  1     2      3      4      5      6       7      8     9
       ┌─────┬──────┬──────┬──────┬──────┬───────┬──────┬─────┬──────┐
       │ usr │ ass  │ tool │ ass  │ tool │ tool  │ ass  │tool │ ass │
       └─────┴──────┴──────┴──────┴──────┴───────┴──────┴─────┴──────┘
         └────────── turnPrefixMessages ──────────┘  └─ kept ─┘
       turnStart=1，entries 1-6                         entries 7-9

       切点在 entry 7（assistant），但 entry 1（user）是它的 Turn 起点
       → entry 1-6 是"被切断的 Turn 前缀"，单独生成 turnPrefix 摘要
       → entry 7-9 留在保留区
```

源码里 Pi 把这部分叫做 **turnPrefixMessages**——用专门的 `TURN_PREFIX_SUMMARIZATION_PROMPT` 单独生成前缀摘要。实现先生成主历史摘要（若有需要），再生成 turn-prefix 摘要，然后合并成一个摘要文本；这两次 summarization 调用是顺序执行的。

注意主摘要和 turnPrefix 摘要的分工不同：
- **主摘要**覆盖切分 turn 之前的历史 → 用 6 section 结构化格式
- **turnPrefix 摘要**覆盖从 turn 起点到保留区切点之前的消息 → 用更轻量的 3 段格式（Original Request / Early Progress / Context for Suffix）

两份摘要合并后存储在同一个 CompactionEntry 里，下一轮 buildSessionContext 时一起注入。LLM 看到的是一份完整的"压缩前发生了什么 + 半个 Turn 的前缀"。

## 六、压缩结果如何生效

§一末尾已经讲了核心时序——压缩在两轮之间发生。这一节展开"压缩结果如何影响下一次运行"。

压缩完成后，结果怎么影响后续的 Agent 运行？

### CompactionEntry：压缩结果的物理形态

每次压缩产生一个 `CompactionEntry`，它存储在 Session Tree 上（第 10 章详讲）：

```typescript
const entry = {
    type: "compaction",
    summary: "## Goal\nFix auth.ts...\n## Progress\n...",   // 摘要文本
    tokensBefore: 185000,              // 压缩前 token 数（用于诊断和审计）
    firstKeptEntryId: "e30",           // 保留的起始 entry id（重建上下文时从这开始）
    details: {                         // 文件操作跟踪
        readFiles: ["src/utils/hash.ts"],
        modifiedFiles: ["src/auth.ts"],
    },
};
```

写入 session 时还会由 `SessionManager` 补上 entry 的 id、parentId 与 timestamp 等字段。`tokensBefore` 来自准备阶段的当前上下文 token 估值；它可能使用 usage 加尾部估算，不保证一定是 tokenizer 实测值。

### 上下文重建

`SessionManager.buildSessionContext()` 沿当前 leaf 的父链重建上下文：遇到最新 compaction entry 时加入一条 summary message，再从该 entry 的 `firstKeptEntryId` 指定位置收集后续保留 entries。不是把旧树节点删除，而是在本次 LLM context 中选择“摘要 + 保留区”：

```
重建后的上下文：
├── CompactionSummaryMessage（role: "compactionSummary"）
│     content = 摘要文本
│     （第6章讲过：convertToLlm 把它翻译成 UserMessage）
│
├── 保留的原始消息（从 firstKeptEntryId 起的当前路径后缀）
│     ├── UserMessage: "继续修复"
│     ├── AssistantMessage: ...
│     └── ...
│
└── （新的消息会在运行中追加）
```

回忆第 6 章的消息系统：`CompactionSummaryMessage` 是 coding-agent 的自定义消息类型，`convertToLlm` 会把它转换成一条 user message，并用固定前后缀包裹摘要文本。LLM 看到的是“此前历史被压缩为以下摘要”这类上下文标记。

**对 LLM 来说，之前的几十轮对话变成了一个摘要。** 它不知道原始消息的细节，但它知道目标、进度、决策和文件操作记录——这对继续工作来说通常够用了。

### 自动压缩的集成

自动压缩由 `AgentSession._checkCompaction()` 和 `_runAutoCompaction()` 调度，不是低层 `Agent` 的自动行为：

```
正常路径：agent_end 后检查；提交下一条 prompt 前也会检查上次响应
    │
    ▼
检查 overflow / recoverable length / shouldCompact()？
    │
    ├── 不需要 → 结束
    │
    └── 需要 → 执行压缩
         ├── findCutPoint → 找切割点
         ├── session_before_compact 扩展钩子可取消或提供自定义结果
         ├── 序列化 + LLM 调用 → 生成摘要
         ├── 追加 CompactionEntry 到 Session Tree
         └── AgentSession 重建消息状态
```

Overflow recovery 有明确的重试边界：如果响应是成功的 `stop`，即便识别为 silent overflow，也只压缩并保留已完成回答，不调用 `continue()` 重试。若响应是 overflow error 或可恢复的 length stop，首次会从 agent 当前消息状态中移除失败 / 截断 assistant 消息，保留 session history 记录，压缩后最多继续一次。每条当前 user message 只允许一次 overflow recovery；再次失败会发出失败事件，不再循环重试。被用户中止的响应通常跳过检查，但下一条 prompt 前的补查可以纳入 aborted 响应后的上下文估算。

这和普通网络 / provider 重试是两套逻辑：transient error 使用单独 retry 设置与退避；context overflow 不交给通用错误重试。摘要生成本身也通过 `retryAssistantCall` 处理可重试的瞬时流错误。手动 compact 是另一入口，不会续跑被打断的 agent turn。

### 两套事件

压缩过程会发出两种事件（第 7 章讲过的 Session 层扩展事件）：

- `compaction_start`（reason: "manual" | "threshold" | "overflow"）
- `compaction_end`（携带压缩结果或错误信息）

UI 可以订阅这些事件来显示"正在压缩上下文..."的进度提示。

## 七、完整链路回顾

把全章串起来，一次压缩的完整旅程：

<Diagram file="/assets/260702-ch09-compaction-flow.svg" caption="压缩的完整链路" id="260702-ch09-compaction-flow" />

**配图说明**：6 步横向流程——检查阈值或 overflow→找切割点→分割→生成摘要→存 CompactionEntry→重建 AgentSession context。图中的 185K / 200K 是示例数值；threshold 和 overflow recovery 后是否继续 turn，取决于触发分支。

```
① 触发检查（AgentSession）
   valid usage / fallback estimate → shouldCompact()
   或者识别 context overflow / recoverable length stop

② 找切割点
   向后遍历 → 累积 token 到 keepRecent(20K) → 找最近的有效切割点
   排除 toolResult，并在上一次 compaction 边界之后搜索

③ 分割消息
   切割点之前 → messagesToSummarize（被压缩）
   切割点之后 → kept（保留）

④ 生成摘要
   序列化消息为文本 → 调 LLM 填写 6 section 结构化摘要
   split turn 时再顺序生成 turn-prefix 摘要 → 合并文件跟踪列表

⑤ 存储结果
   CompactionEntry 追加到 Session Tree

⑥ 重建 session context / 恢复（按触发原因）
   buildSessionContext() → summary message + firstKeptEntryId 后缀
   threshold / 成功 stop overflow：不重试已完成响应
   overflow error / recoverable length：至多 continue 一次
```

## 八、设计精华

回顾整章，Pi 的压缩算法有三个值得带走的设计思路。每个都不是"为了巧而巧"，而是为了回应一个具体的工程张力。

### 1. 向后遍历 + 合法切点：保护最重要的东西

`findCutPoint` 不是"找哪里能切"，而是"找哪里值得保留"——**从最新消息往回走**，直到累积够 `keepRecentTokens`（默认 20K）。这种"逆向"思路背后的判断是：**最近的上下文最重要**——模型需要"刚才读了什么""用户最新说了什么"，比"10 轮前讨论了什么"关键得多。

切点排除 `toolResult` 是因为协议约束——toolResult 必须紧跟 toolCall，否则模型会"调了工具但找不到结果"。这是个不可妥协的硬约束。

> 实现：`packages/coding-agent/src/core/compaction/compaction.ts` 的 `findCutPoint` 与 `findValidCutPoints`

### 2. 结构化摘要：用固定模板对抗 LLM 的"自由发挥"

`SUMMARIZATION_PROMPT` 强制 LLM 填 6 个固定 section：Goal / Constraints & Preferences / Progress（含三个子项：Done / In Progress / **Blocked**）/ Key Decisions / Next Steps / Critical Context。其中 Progress 的 Blocked 子项专门记录"卡住的事"——LLM 在新一轮里看到这条，可以优先尝试解锁。

为什么不写"请总结对话"？因为自由文本摘要有一个失败模式：LLM 容易被"有趣的内容"吸引，花大篇幅描述某个技术细节，**忘了记录用户的核心需求**。固定 section 强制 LLM 在每个维度上至少扫一遍，把"易遗漏"变成"必须填"。

加上增量更新（`UPDATE_SUMMARIZATION_PROMPT`）——多次压缩时新摘要是在旧摘要基础上更新，不是从零重写。这避免了"每次压缩摘要漂移一点"的累积误差。

**这是用 prompt 设计约束摘要结构的范例**——固定模板 + 增量更新为模型提供了需要覆盖的信息维度；这是一种设计意图，不等于摘要无损，也没有在本章测量它对遗漏率的改善。

> 实现：`packages/coding-agent/src/core/compaction/compaction.ts` 的 `SUMMARIZATION_PROMPT` 与 `UPDATE_SUMMARIZATION_PROMPT`

### 3. 文件跟踪累积：编码 Agent 的领域特定知识

`extractFileOperations` 从两个来源累积文件列表：
1. 上一次由 Pi 生成的压缩结果的 `details.readFiles` / `modifiedFiles`
2. 这次被压缩消息中的 `read`、`edit`、`write` 工具调用

最终把只读文件和已写入 / 编辑文件分别用 `formatFileOperations` 格式化为 `<read-files>...</read-files>` 与 `<modified-files>...</modified-files>`，再附加到摘要末尾。已经修改的文件不会同时保留在只读列表中。

为什么单独跟踪文件？因为对编码 Agent 来说，"**改过哪些文件**"是至关重要的元信息——比"对话里讨论过什么"更精确、更可验证。LLM 看到这个列表，知道哪些文件已经被项目触碰过，避免重复读、避免覆盖他人改动。这是一种"领域知识嵌入到通用机制"的做法——压缩算法本身是通用的，但通过 `details` 字段承载领域特定信息。

> 实现：`packages/coding-agent/src/core/compaction/compaction.ts` 的 `extractFileOperations` 与 `computeFileLists`；标签格式化在 `packages/coding-agent/src/core/compaction/utils.ts` 的 `formatFileOperations`
