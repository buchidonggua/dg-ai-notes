## 一、问题：会话数据怎么存？

前 8 章我们一直在跟 `context.messages` 打交道——它是一个数组，存着当前轮的对话。但每次 Agent 启动时，这个数组从哪来？关闭后到哪去？

这就引出一个最基础的工程问题：**会话数据怎么存？**

这个问题其实**包含两个独立的子问题**，需要拆开看：

- **子问题 A：存在哪里？**（存储介质）
- **子问题 B：长什么样？**（数据结构）

两个维度是正交的——你可以"用 mysql 存线性数组"，也可以"用 JSONL 文件存一棵树"。混淆它们会让后续讨论糊成一团。下面分别展开。

### 子问题 A：存在哪里？（介质）

如果你做过后端开发，第一反应可能是把对话写进关系型数据库——一张 messages 表，按会话 id 分组查询。

Pi 的 coding-agent **没有走这条路**。它选了**本地 JSONL 文件**——每个会话一个 `.jsonl` 文件，一行一个 entry，纯文本。默认目录在用户家目录下的 `~/.pi/agent/sessions/<编码后的 cwd>/`，不会写进项目的 `.pi/sessions/`。改变 `PI_CODING_AGENT_DIR` 会改变这个用户级数据根目录；CLI 也允许用 `PI_CODING_AGENT_SESSION_DIR` 或 `--session-dir` 指定会话目录。

源码能确认的是文件布局和存储接口；下面列的是这种实现带来的使用结果，不把它们当成源码明说的设计动机：

- **本地 CLI 使用**：会话保存在用户目录，使用时不需要另行部署数据库服务；这不代表运行时不存在并发场景
- **按工作目录分开**：`cd /project-a` 和 `cd /project-b` 会映射到不同的 cwd 编码子目录；会话仍集中在用户级数据目录，项目里不需要留下 `.pi/sessions/`
- **部署简单**：不需要单独配置数据库服务
- **可读、可调试**：JSONL 是纯文本，可以 `cat` / `grep` / 用编辑器直接打开看，调试时一目了然

但 Pi 没有把这条路焊死。agent-core 在 `packages/agent/src/harness/session/types.ts` 定义了 `SessionStorage` 和 `SessionRepo` 抽象，另有 JSONL、内存及 SQLite 仓储实现。**注意**：coding-agent 的 `SessionManager` 在 `packages/coding-agent/src/core/session-manager.ts` 自己定义了 `SessionEntry` 和 v3 文件格式，既不实现 agent-core 的 `SessionStorage`，也不共享它的 `Entry` 联合类型。两者是独立的两套会话实现；理解这个边界，后面看 v3 与 v4 的差异就不会误以为只是同一套代码换了存储介质。

> 实现：`packages/agent/src/harness/session/types.ts` 的 `SessionStorage` / `SessionRepo`；`packages/agent/src/harness/session/jsonl/repo.ts` 的 `JsonlSessionRepo`；`packages/session-backends/sqlite-node/src/sqlite/repo.ts` 的 `SqliteSessionRepository`；`packages/coding-agent/src/core/session-manager.ts` 的 coding-agent `SessionManager`

所以"存在哪里"这一层的选择是：**coding-agent 默认用用户目录下的 JSONL 文件；agent-core 则提供独立的仓储抽象和多种后端**。这层搞清楚了，下一层问题才好讨论。

### 子问题 B：长什么样？（结构）

存哪里解决了，但还有更深一层的问题：**对话数据的逻辑形态是什么？**

最直觉的答案：**线性数组**。`messages = [msg1, msg2, msg3, ...]`，一条接一条。这种结构最简单，也是 mysql 那种 messages 表默认的形态。

但真实使用场景里，对话**不总是线性的**：

- **重试**：Agent 的回复不好，你想"退回上一轮"重新生成
- **分支**：你想在某个节点尝试两种不同的方案，比较结果
- **回退**：走了一条路发现不对，想回到之前的岔路口

如果数组只保存当前有效路径，这些操作就意味着"删掉后面的消息再重写"。要同时保留两条分支，就得额外记录分支关系或保存多份副本；比如先试方案 A 走到底，再回过头试方案 B，A 的对话记录也得留着对比。

朴素的单路径数组不直接表达"分叉且保留两边记录"。Pi 的 coding-agent 用 **Session Tree** 按 `parentId` 组织对话；常规回退不删除旧 entry，而是移动内存中的指针，继续对话时再追加新 entry。迁移和分支副本等流程仍会重写文件，见第六节。

| 维度 | 一般选择 | Pi 的选择 |
|------|---------|----------|
| 存哪里 | mysql 等数据库 | 用户级目录中的 JSONL 文件（目录可配置） |
| 长什么样 | 单一路径数组 | 树（Session Tree，常规操作追加新 entry） |

下面用一个具体会话示例，带你一步一步看这棵树如何长出来。

## 二、跟着一次会话示例看树怎么长出来

抽象地讲"常规追加与回退构成一棵 append-only 的树"几乎没人能看懂。我们用一个具体场景：**调试一个认证 bug**。

设想你打开 Pi Agent，进行 8 步操作：

```
步骤 1: 切换到 Claude 4.6 模型（你想用更聪明的模型）
步骤 2: 你问 "auth.ts 里 salt 验证为什么失败？"
步骤 3: Agent 决定调 read 工具读 auth.ts
步骤 4: read 工具返回 auth.ts 的内容
步骤 5: Agent 分析后回复 "问题在 23 行，salt 没编码"
步骤 6: 你不太满意这个回答，回退到步骤 2 重来
步骤 7: 你换思路问 "先看 hash 函数的实现"
步骤 8: Agent 调 grep 找到 hash 函数并给出新的分析
```

下面看这 8 步怎么让会话树从"空"长成一棵有分支的树。为方便阅读，`e1` 到 `e9` 是教学代号；真实 entry ID 是经碰撞检查的短十六进制串。

### 第 1 步：切换模型，第一个节点上树

会话启动时，文件第一行是 Session Header（不是树节点，是文件元信息）。然后你切换模型，产生第一个真正的树节点 `ModelChangeEntry`：

```
e1: ModelChangeEntry
    parentId: null（根节点）
    payload: { model: "claude-sonnet-4-6" }
```

这棵树现在只有一个节点：

```
e1 (model_change)
↑
leafId 在这
```

### 第 2 步：你提问，UserMessage 节点上树

你输入"auth.ts 里 salt 验证为什么失败？"，产生第二个 `type: "message"` 节点，代码中的类型名是 `SessionMessageEntry`：

```
e2: SessionMessageEntry（type: "message"）
    parentId: e1
    message:
      role: "user"
      content: [{ type: "text", text: "auth.ts 里 salt 验证为什么失败？" }]
```

注意 `parentId: e1`——它指向"上一个节点"，不指向 session header。树形：

```
e1 (model_change)
 └── e2 (user message)
       ↑
     leafId
```

### 第 3 步：Agent 调 read 工具，AssistantMessage 节点上树

Agent 决定先读文件，产生一个含 ToolCall 的 AssistantMessage：

```
e3: SessionMessageEntry（type: "message"）
    parentId: e2
    message:
      role: "assistant"
      content: [
        { type: "text", text: "让我读一下 auth.ts" },
        { type: "toolCall", id: "call_001", name: "read",
          arguments: { path: "src/auth.ts" } }
      ]
      stopReason: "toolUse"
```

这一条 AssistantMessage **同时包含文本和工具调用**——它们放在同一个 content 数组里，是同一个节点。不是"文本一个节点 + 工具调用一个节点"。这点第 6 章讲过，但读者容易忘，再强调一次。

```
e1 (model_change)
 └── e2 (user)
      └── e3 (assistant + ToolCall)
            ↑
          leafId
```

### 第 4 步：read 工具返回结果，ToolResult 节点上树

工具执行完，产生一个 ToolResult 消息节点：

```
e4: SessionMessageEntry（type: "message"）
    parentId: e3
    message:
      role: "toolResult"
      toolCallId: "call_001"     ← 关联到 e3 里的 ToolCall
      content: [{ type: "text", text: "export function verifySalt(s) { ... }" }]
      isError: false
```

注意 `toolCallId` 字段——它把这条 ToolResult 和触发它的 ToolCall 关联起来。这是第 5 章讲过的"工具结果必须精准关联回调用请求"在数据层的体现。

```
e1 (model_change)
 └── e2 (user)
      └── e3 (assistant + ToolCall)
           └── e4 (toolResult)
                 ↑
               leafId
```

### 第 5 步：Agent 给出分析，又一个 AssistantMessage

Agent 看到文件内容后回复分析：

```
e5: SessionMessageEntry（type: "message"）
    parentId: e4
    message:
      role: "assistant"
      content: [{ type: "text", text: "问题在 23 行，salt 没编码" }]
      stopReason: "stop"
```

到现在为止，5 步操作产生了 5 个节点，全部挂在一条直线上——这就是"主分支"：

```
e1 (model_change)
 └── e2 (user: "salt 验证为什么失败?")
      └── e3 (assistant: read auth.ts)
           └── e4 (toolResult: auth.ts 内容)
                └── e5 (assistant: "问题在 23 行")
                      ↑
                    leafId
```

到这里你看到了"追加操作"——每一步只做两件事：创建新节点（带 parentId）+ 移动 leafId。没有任何旧节点被修改。

### 第 6 步：回退——这是关键转折

你对"问题在 23 行"这个分析不太满意，想换个思路。这时你执行**回退**——但**没有删除任何节点**：

```text
branch("e2")
  ├─ 检查 byId 中是否存在 e2
  └─ leafId = "e2"       // 只改当前 SessionManager 的内存状态
```

这里展示的是底层 `SessionManager.branch("e2")`：leaf 直接指向 e2。交互界面若用 `navigateTree()` 选中 user entry e2，则会回到它的 parent e1，并把 e2 的文本放回编辑器；§四 会用这个 UI 行为解释分支摘要的位置。

操作只有一行：`leafId = "e2"`。回退后树长这样：

```
e1 (model_change)
 └── e2 (user: "salt 验证为什么失败?")
      ├── e3 (assistant: read auth.ts)        ← 旧分支还在
      │    └── e4 (toolResult)                     数据完整保留
      │         └── e5 (assistant: "问题在 23 行")
      │
      ↑ leafId 现在指回 e2
```

**e3、e4、e5 一个都没删**——它们还在树上，只是不在"当前路径"上。这就是 append-only 的核心：**回退不是删数据，是移动指针**。

为什么要保留？因为你不知道以后会不会想回到旧分支。也许新思路走半天没结果，你想退回去看原来的"问题在 23 行"分析。如果回退时删了，就再也找不回来了。

### 第 7 步：换思路重新问——新分支自然长出

你从 e2 这条岔路口换了一个问题，产生新节点：

```
e6: SessionMessageEntry（type: "message"）
    parentId: e2   ← 跟 e3 共享同一个父！
    message:
      role: "user"
      content: [{ type: "text", text: "先看 hash 函数的实现" }]
```

注意——e6 的 `parentId` 也是 `e2`，跟 e3 一样。这是分支的本质：**两个节点共享同一个 parent，就是树上的两个分支**。

```
e1 (model_change)
 └── e2 (user: "salt 验证为什么失败?")
      ├── e3 (assistant: read auth.ts)
      │    └── e4 (toolResult)
      │         └── e5 (assistant: "问题在 23 行")
      │
      └── e6 (user: "先看 hash 函数")    ← 新分支起点
            ↑
          leafId
```

### 第 8 步：新分支继续长

Agent 在新分支上调 grep，产生 3 个新节点（assistant + toolResult + assistant）：

```
e1 (model_change)
 └── e2 (user: "salt 验证为什么失败?")
      ├── e3 (assistant: read auth.ts)
      │    └── e4 (toolResult)
      │         └── e5 (assistant: "问题在 23 行")
      │
      └── e6 (user: "先看 hash 函数")
           └── e7 (assistant: grep hash)
                └── e8 (toolResult: grep 结果)
                     └── e9 (assistant: 新分析)
                           ↑
                         leafId
```

到这里这份会话记录有 9 个节点，分成两个分支。常规回退和追加没有删除 e3-e5；你可以回到 e5 那条路径，也可以在 e9 这个分支继续推进。

这就是 Session Tree 的基本操作：**entry 以父节点连接成树，回退先移动内存中的指针，再从新位置追加 entry 来形成分支**。如果只调用 `branch()` 而没有追加新 entry，这次指针移动不会单独写进 JSONL；此时重开会话会从文件末尾的 entry 重建 leaf。正常追加与回退不会改写旧 entry；迁移和分支副本等路径另有全文件重写。

<Diagram file="/assets/260702-ch10-session-tree.svg" caption="Session Tree：常规操作中的 append-only 状态变化" id="260702-ch10-session-tree" />

**配图说明**：三幅快照展示树的演化——① 当前在 A2 → ② 回退到 A1（只移动内存中的 leafId，A2 仍保留）→ ③ 从 A1 追加新分支 B1→B2。常规回退不删除 entry；追加新 entry 后，新的路径才会写入会话文件。底部图例：红色 = 当前 leafId，绿色 = 新分支，虚线灰 = 仍保留的旧分支。

## 三、树上节点的解剖

看完树怎么长出来，我们仔细看节点本身。

### 一条 SessionMessageEntry 长这样

第 3 步产生的那条 AssistantMessage，在 `.jsonl` 文件里是一行 `type: "message"` 的 JSON。下面是摘录；`id` 和 `parentId` 使用前文教学代号以便对照，时间是示意值：

```json
{
  "type": "message",
  "id": "e3",
  "parentId": "e2",
  "timestamp": "2026-07-03T10:23:45.000Z",
  "message": {
    "role": "assistant",
    "content": [
      { "type": "text", "text": "让我读一下 auth.ts" },
      { "type": "toolCall", "id": "call_001", "name": "read",
        "arguments": { "path": "src/auth.ts" } }
    ],
    "model": "claude-sonnet-4-6",
    "stopReason": "toolUse",
    "usage": { "input": 1250, "output": 80 }
  }
}
```

读这串 JSON 你就明白了 Session Tree 的全部精髓：

| 字段 | 干什么 | 设计动机 |
|------|--------|---------|
| `type: "message"` | 区分 entry 类型 | `SessionMessageEntry.message` 保存完整的 `AgentMessage`；不只 user / assistant / toolResult，也可容纳 coding-agent 的 bash execution 等消息 |
| `id: "e3"` | 节点唯一标识 | 别的节点通过 parentId 指向它 |
| `parentId: "e2"` | 指向父节点 | **认父不认子**——节点不知道自己有哪些子节点 |
| `timestamp` | 创建时间 | 排序、调试用 |
| `message` | 真正的消息载荷 | `AgentMessage` 的 role、content、model 等字段（第 6 章讲过） |

**关键点：`parentId` 是单向的**。节点知道自己从哪来（parentId），但父节点不知道自己有哪些孩子。这不是疏忽，是设计——如果父节点要维护 children 列表，追加新子节点时就得修改父节点，违反 append-only 原则。**所以"认父不认子"是 append-only 的必要条件**。

### 9 种 Entry 类型，按职责分三组

第 2 节那个例子里出现了 `model_change`、`user`、`assistant`、`toolResult` 四种节点。其实 Pi 一共定义了 9 种 Entry 类型。看起来多，其实**按"对 LLM 调用的影响"分三组**就清晰了：

**第一组：进 LLM 上下文（4 种）**

这 4 种会参与当前 LLM 上下文，经过 `sessionEntryToContextMessages()` 后成为 `AgentMessage`：

| 类型 | 产生什么消息 | 例子 |
|------|------------|------|
| `SessionMessageEntry`（`type: "message"`） | 直接携带 `AgentMessage`，可含 user、assistant、toolResult、custom、bashExecution 等消息 | 第 2-5 步的对话与工具过程 |
| `CustomMessageEntry`（`custom_message`） | 转成扩展注入的 custom message | 扩展加入上下文的内容 |
| `CompactionEntry`（`compaction`） | 转成 `CompactionSummaryMessage` | 第 9 章讲的压缩结果 |
| `BranchSummaryEntry`（`branch_summary`） | 转成 `BranchSummaryMessage` | 后面 §四 讲的分支摘要 |

**第二组：影响后续 LLM 调用（2 种）**

这 2 种不产生消息，但改变后续 LLM 调用的参数：

| 类型 | 改变什么 | 例子 |
|------|---------|------|
| `ModelChangeEntry`（`model_change`） | 更新上下文中的 provider / model | 第 1 步切到 Claude 4.6 |
| `ThinkingLevelChangeEntry`（`thinking_level_change`） | 更新思考级别 | 用户调整思考强度 |

**第三组：纯元数据，不影响 LLM（3 种）**

这 3 种既不产生消息、也不改 LLM 参数，纯粹是给 UI 或扩展用的：

| 类型 | 干什么 |
|------|--------|
| `LabelEntry`（`label`） | 给节点贴书签（"这里是关键点"） |
| `SessionInfoEntry`（`session_info`） | 保存会话显示名称（`name`） |
| `CustomEntry`（`custom`） | 扩展自己存的元数据 |

**为什么要把类型分这么细？** 因为 `buildSessionContext()`（下一节讲）需要按类型分派处理——消息类 entry 转成上下文消息，模型和思考级别 entry 更新状态，元数据 entry 则不进上下文。如果只有一种类型，处理逻辑就得塞满 `if-else`，可读性和扩展性都差。

<Diagram file="/assets/260702-ch10-entry-taxonomy.svg" caption="coding-agent v3 SessionEntry 的 9 种类型" id="260702-ch10-entry-taxonomy" />

**配图说明**：图里只画 coding-agent 自己的 v3 `SessionEntry` 联合类型。9 种 entry 共享基础字段（type / id / parentId / timestamp），按 `buildSessionContext()` 的处理分三组——① 参与上下文（4 种）；② 更新 model / thinkingLevel（2 种）；③ 纯元数据（3 种，跳过上下文）。agent-core 的 Entry 类型不同，不在这张图里。

> 类型定义在 `packages/coding-agent/src/core/session-manager.ts` 的 `SessionEntry` 联合类型

### 为什么"认父不认子"是 append-only 的必要条件

回到 `parentId` 这个设计。如果改成"认子不认父"——子节点没 parentId，但父节点有 children 列表——会发生什么？

回到第 7 步，你要从 e2 长出新分支 e6。如果是"认子"，e2 的 children 列表从 `[e3]` 改成 `[e3, e6]`——**这需要修改 e2**。但 append-only 规定节点不可变，这就矛盾了。

所以**只有"认父不认子"才能让追加操作不修改任何旧节点**。这是个看似违反直觉（"树通常父节点知道子节点"）但完全合理的设计。

---

## 四、三个核心操作 + 分支摘要

有了第 2 节的具体例子，现在可以把三个核心操作 + 分支摘要一起讲清楚。

### 操作 1：追加——内存索引更新与落盘分开看

追加操作只有三步：

```
1. 创建新 Entry（含自己的 id、parentId 指向当前 leafId、payload）
2. 存入 byId 映射表（id → entry）
3. leafId = 新 entry 的 id
```

回到第 3 步（产生 e3 节点）：

```text
sessionManager.appendMessage(assistantMessage);
→ 创建 SessionMessageEntry（parentId = e2），加入 fileEntries 和 byId；leafId 移到新 entry；_persist() 再决定是否写入
```

`byId` 写入和 `leafId` 赋值只是内存索引更新；这不表示整个追加过程是 O(1)。生成 ID 时要检查碰撞，`_persist()` 会扫描已有 entry 判断是否已出现 assistant message，随后还要同步写文件。**追加没有修改 e2**——只是创建 e3 时让它的 parentId 指向 e2。e2 完全不知道自己多了个孩子；`getChildren()` 会扫描 entry 列表来反查指向它的子节点。`byId` 映射表用于按 ID 找 entry，不是子节点索引。这就是"认父不认子"：**entry 只保存父引用，父 entry 不维护 children 列表**。

### 操作 2：回退——只移动 leafId

```text
branch(branchFromId: "e2"): void {
    if (!this.byId.has(branchFromId)) {
        throw new Error(`Entry ${branchFromId} not found`);
    }
    this.leafId = "e2";   // 核心就是这一行
}
```

**内存中的核心就是 `leafId = branchFromId`**（外加一个 `byId` 存在性检查）。没有删除 e3、e4、e5——它们仍在内存索引和原 `.jsonl` 文件里。裸 `branch()` 不持久化 leaf 指针；如果此时重开而且还没有追加新 entry，`_buildIndex()` 会按文件顺序把最后一个 entry 当作 leaf。回退后继续追加，新的 entry 才会以 e2 为 parentId 写进文件。

### 操作 3：分支——回退后追加的自然结果

回退到 e2 后再追加 e6，e6 的 parentId 自动就是 e2——这就是分支。**分支不是独立的操作，是"回退 + 追加"的组合效果**。

### 分支摘要：BranchSummaryEntry——回退时的可选项

回到第 6 步。你从 e5 回退，旧分支（e3-e5）就成了"被抛弃的分支"。这些 entry 仍在会话记录里，但**当前路径的 LLM 看不到它们**（因为 `buildSessionContext()` 只走当前路径）。

有时候你希望当前路径的 Agent **大致知道**之前试过什么——不用看完整对话，知道个大概就行。比如"之前的尝试发现 salt 编码有问题，但没解决根因"。这时你可以用 `branchWithSummary()`：

这里要先区分低层 API 和 UI 导航。第二节里的低层 `branch("e2")` 会把 leaf 直接移到 e2；若直接调用 `branchWithSummary("e2", summary)`，摘要 entry 的 parentId 也会是 e2。下面的树专门展示 UI 情况：`AgentSession.navigateTree("e2", { summarize: true })` 选中的是 user entry，实际导航位置是它的 parent e1，问题文本则回到编辑器。UI 流程可先异步生成摘要；生成成功后，底层同步 `branchWithSummary("e1", summary)` 记下旧 leaf 并把摘要作为 e1 的子节点追加。摘要完成前若被取消，不会移动 leaf。

挂上去后树变成：

```
e1 (model_change)
 ├── e2 (user: "auth.ts 里 salt 验证为什么失败?")
 │    └── e3 → e4 → e5 (旧路径仍保留)
 └── e_BranchSummary (parentId: e1, fromId: e5)
      └── e6 (下一条 user message 的 parentId 是摘要 entry)
```

图中的 `e6` 是之后重新发送问题产生的新 user entry，所以它是摘要的子节点，而不是摘要的兄弟节点。低层 `branchWithSummary()` 则严格按传入的目标 ID 设置摘要的 `parentId`。

**BranchSummaryEntry 跟普通消息的区别**：它是被抛弃分支的"遗言"，不是真实发生的对话。`sessionEntryToContextMessages()` 会把它转换成 `BranchSummaryMessage`；压缩节点则变成另一种 `CompactionSummaryMessage`。之后 `convertToLlm()` 会把这些内部消息映射成 LLM 可用的 user message，但它不会合并相邻的 user message。所以新分支的 Agent 会看到："之前尝试过 X，结论是 Y"——它知道了历史，但不会被旧分支的细节淹没。

**这是可选的**——如果你觉得旧分支完全不重要，直接 `branch()` 就够了，不生成摘要。`branchWithSummary()` 是给"想保留历史精华但不想保留完整对话"的场景准备的。

> 实现：`packages/coding-agent/src/core/session-manager.ts` 的 `SessionManager.branchWithSummary`；LLM 摘要生成和可取消流程在 `packages/coding-agent/src/core/agent-session.ts` 的 `AgentSession.navigateTree`

## 五、从树到 LLM 上下文：buildSessionContext

树长好了，但 **LLM 不认识树**。LLM 的 API 只接受一个**线性 messages 数组**（第 6 章讲过：user / assistant / toolResult 三种）。所以每次调用 LLM 之前，要把树"压扁"成数组。这就是 `buildSessionContext()` 的工作。

### 为什么这一步必须存在

想象 LLM 的视角：你给它发一个 HTTP 请求，body 里是 `messages: [...]`——一个数组。它不知道你的会话历史是树形还是数组，它只看 messages 数组。

所以无论你的内部数据结构多复杂，**到 LLM 边界必须变成线性**。这是 Session Tree 的"出口"——树的存储形态是树形，但出口形态是线性的 messages 数组。

### 第一步：路径遍历——从 leaf 往回走到 root

回到我们的例子，当前 leafId 是 e9。`buildSessionContext()` 调用 `buildSessionPath()`，从 e9 沿 parentId 往回走到根，再反转成 root → leaf：

```typescript
const path: SessionEntry[] = [];
let current = byId.get(leafId);   // e9
while (current) {
    path.push(current);   // 先按 leaf → root 顺序收集
    current = current.parentId ? byId.get(current.parentId) : undefined;
}
path.reverse();           // 反转为 root → leaf 顺序
```

走完之后，path 数组（从 root 到 leaf 的顺序）是：

```
[e1, e2, e6, e7, e8, e9]
```

**注意 e3、e4、e5 不在 path 里**——它们不在当前分支上。这就是"当前路径"的含义——只看 leaf 到 root 这一条线，其他分支的数据不会发给 LLM。

### 第二步：按类型分派处理

路径上的每个 entry，按类型决定怎么处理：

```
e1 (model_change)   → 更新状态变量 model = "claude-sonnet-4-6"，不进 messages
e2 (user message)   → 推入 messages 数组
e6 (user message)   → 推入 messages 数组
e7 (assistant + ToolCall) → 推入 messages 数组
e8 (toolResult)     → 推入 messages 数组
e9 (assistant)      → 推入 messages 数组
```

最后构建出来的 messages 数组长这样：

```text
[
  { role: "user", content: "auth.ts 里 salt 验证为什么失败?" },        // e2
  { role: "user", content: "先看 hash 函数的实现" },                    // e6
  { role: "assistant", content: [{ text: ... }, { toolCall: grep ...}] }, // e7
  { role: "toolResult", toolCallId: "call_002", content: ... },        // e8
  { role: "assistant", content: [{ text: "新分析..." }] }              // e9
]
```

注意一个微妙的事情：**e2 和 e6 都是 user 消息，连续两条 user**。`buildSessionContext()` 会照路径保留它们；coding-agent 的 `convertToLlm()` 负责把 bash/custom/摘要等内部消息映射成标准 LLM 消息，不会在这里合并相邻 user。具体 API 适配由后续 provider 层处理。

### 状态变量：覆盖式提取

model_change 和 thinkingLevel_change 不进 messages 数组，但它们影响"用什么参数调用 LLM"。提取方式是**覆盖式**——沿路径从 root 走到 leaf，遇到变更就覆盖：

```
e1 (model_change)   → 更新 model = { provider: "anthropic", modelId: "claude-sonnet-4-6" }
路径上的 assistant message → 也会用它自己的 provider / model 覆盖当前值
e2-e9（没有后续模型信息） → model 变量保持最近一次记录
```

`getSessionContextSettings()` 沿路径检查 `model_change` 和 assistant message；遇到任一种都会覆盖当前值，最后一条模型信息生效。`thinking_level_change` 同样按路径顺序覆盖。

> **模型恢复发生在运行时**：`buildSessionContext()` 的初始 `model` 是 `null`，但它也会从路径上的 assistant message 读取 provider / model。如果创建 session 时显式传入 `model`，`sdk.ts` 以显式值优先；没有显式值时，且会话已有 messages，才尝试恢复历史模型，并要求该模型存在且 provider 已配置认证。无法恢复时再回退到设置中的默认模型。树导航只重建 `agent.state.messages`，不会随之切换当前 `AgentSession.model`。

**为什么把"切换模型"也存成节点？** 节点能记录切换发生在路径的哪个位置；回退后 `getSessionContextSettings()` 只沿新路径读模型变更和 assistant message，旧分支上的模型记录不会参与计算。运行时是否采用历史模型，还要经过显式 model 与 provider 认证检查。

### CompactionEntry 的特殊处理：选择性收集

第 9 章讲压缩时说"压缩结果替换掉被压缩的旧消息"——具体怎么替换，就在这一步。假设路径上有 CompactionEntry：

```
e1 (user)              ← 这之前是早期对话（已被压缩）
e2 (assistant)         ← 被压缩
e3 (assistant)         ← 被压缩
e4 (compaction)        ← 压缩节点，记录了 firstKeptEntryId = "e3"
e5 (user)              ← 压缩后保留的近期消息
e6 (assistant)
```

`buildContextEntries()` 找到当前路径上最新的 CompactionEntry，**不是简单地"停止收集之前的消息"**，而是**按 firstKeptEntryId 选择性收集**：

1. 把 e4 放在上下文 entry 列表最前面，之后由 `sessionEntryToContextMessages()` 生成 `CompactionSummaryMessage`
2. 在 e4 **之前**的 entry 中，**只收集 firstKeptEntryId（e3）及之后的**——e1、e2 被丢弃，e3 保留
3. e4 **之后**的所有 entry 正常收集

最终的 messages 数组：

```text
[
  CompactionSummaryMessage (从 e4 生成),   // 替换了 e1、e2
  { role: "assistant", ... },              // e3（保留区第一个）
  { role: "user", ... },                    // e5
  { role: "assistant", ... },              // e6
]
```

**这就是第 9 章说的"压缩结果替换旧消息"的具体实现**——不是真的删 e1、e2（append-only 不允许删），而是 buildSessionContext 在遍历时按 firstKeptEntryId "跳过"它们。下次如果你回退到 e4 之前的位置，buildSessionContext 的路径不包含 e4，e1-e3 又会作为正常消息出现——压缩不是破坏性的，只是"当前路径上"的视图。

注意 firstKeptEntryId 是 CompactionEntry 自己记录的字段——它在压缩发生时就计算好了"保留哪些近期消息"。第 9 章讲的"找切割点"就是为了确定这个 firstKeptEntryId。

> 实现：`packages/coding-agent/src/core/session-manager.ts` 中的 `buildSessionPath`、`getSessionContextSettings`、`buildContextEntries`、`sessionEntryToContextMessages` 和 `buildSessionContext`

## 六、JSONL 持久化的具体细节

§一 已经讲了"为什么选 JSONL 文件"，这一节展开"具体怎么写"。

### 格式：一行一个 Entry

下面是同一教学会话的 JSONL 结构摘录；entry ID 沿用 e1/e2/e3/e6 教学代号，消息字段和时间已精简，不能当作完整会话文件：

```jsonl
{"type":"session","version":3,"id":"0190f7c8-5a8d-7a38-ae3f-2c9a4f6e1b80","timestamp":"2026-07-03T10:00:00.000Z","cwd":"/project"}
{"type":"model_change","id":"e1","parentId":null,"timestamp":"2026-07-03T10:00:05.000Z","provider":"anthropic","modelId":"claude-sonnet-4-6"}
{"type":"message","id":"e2","parentId":"e1","timestamp":"2026-07-03T10:23:00.000Z","message":{"role":"user","content":[{"type":"text","text":"auth.ts 里 salt 验证为什么失败？"}]}}
{"type":"message","id":"e3","parentId":"e2","timestamp":"2026-07-03T10:23:30.000Z","message":{"role":"assistant","content":[{"type":"text","text":"让我读一下 auth.ts"},{"type":"toolCall","id":"call_001","name":"read","arguments":{"path":"src/auth.ts"}}],"stopReason":"toolUse"}}
{"type":"message","id":"e6","parentId":"e2","timestamp":"2026-07-03T10:30:00.000Z","message":{"role":"user","content":[{"type":"text","text":"先看 hash 函数的实现"}]}}
```

第一行是 Session Header（`type: "session"`），记录会话元信息（cwd、版本号等）。后续每行是一个 Entry。

**几个值得注意的细节**：

1. **e6 的 parentId 是 e2**——通过这个字段就能在文件里看出"这里有个分支"。用 `grep '"parentId":"e2"'` 就能找到所有从 e2 长出来的子节点
2. **timestamp 是 ISO 字符串**——人类可读，调试时一眼看出顺序
3. **entry id 通常是 8 位十六进制字符串**（如 `a1b2c3d4`），生成时先检查当前会话有没有撞 ID；尝试 100 次仍冲突才退回完整 UUID。Header 的 session id 则用 UUIDv7。

**为什么用 JSONL 而不是单个 JSON？** 正常已落盘会话追加 entry 时，`_appendEntry()` 会调用 `appendFileSync` 把新行写到文件末尾，不必为了每次追加重写整个文件。迁移和分支副本等路径仍会重写文件，下一小节会说明。

> 实现：`packages/coding-agent/src/core/session-manager.ts` 的 `SessionManager._appendEntry`、`SessionManager._persist`

### 延迟写入：避免"有问无答"的半截对话

有一个写入策略细节：**新会话的文件创建会延迟到首条 assistant message 到来**：

| 时机 | 行为 |
|------|------|
| 新会话还没有 assistant message | 先在内存里积累 entry，不写盘 |
| 首条 assistant message 追加后 | 用 `openSync("wx")` 新建文件，再把 header 和积累的 entry 写进去 |
| 文件已 flushed | 后续 entry 逐条用 `appendFileSync` 追加 |

这主要避免创建后从未得到 assistant message 的空会话立即落盘。`"wx"` 表示以排他方式创建文件，目标已存在时不会覆盖；它**不代表原子写入保证**，批量写入中断仍可能留下不完整文件。首次 assistant message 也可能是工具调用、报错回复或未完成轮次，因此这个策略不保证完整的 user-assistant 往返。首次 flush 之后，新 user entry 会立刻追加，仍可能形成尚未回答的末尾消息。

之后所有 entry 都立即 append；延迟只用于创建会话文件之前的积累阶段。

### 偶尔的全文件重写

虽然日常追加用 `appendFileSync`，源码中调用 `_rewriteFile()` 的场景主要有：

- **初始化空会话文件**：目标文件为空时写入 header
- **旧版本迁移**：v1 / v2 entry 升级到当前 v3 格式后重写
- **创建分支副本**：把所选路径复制到新 `.jsonl` 文件

这不是通用的损坏修复流程：加载器会跳过无法解析的行；如果一个非空文件没有解析成有效的 Pi session，打开时会报错而不是自动重写。重写本身用 `openSync("w")`，会覆盖目标文件，也不承诺原子替换。

> 实现：`packages/coding-agent/src/core/session-manager.ts` 的 `migrateToCurrentVersion`、`SessionManager._setSessionFile`、`SessionManager.createBranchedSession` 和 `SessionManager._rewriteFile`

## 七、两层实现：接口允许换数据库

两套实现都能表达会话历史，但它们的 Entry、落盘格式和状态模型不共享：

| | agent-core harness | coding-agent |
|---|---|---|
| **API 风格** | `SessionStorage` / `SessionRepo` 异步接口 | `SessionManager` 同步接口 |
| **Entry 类型** | 7 种：message、model、thinking、active tools、compaction、branch summary、custom | 9 种：另有 custom_message、label、session_info 等 |
| **其他状态** | 多 lane 游标、操作 records、全局 name / label facts | 单个 leafId；label、session_info、custom 是 Entry |
| **文件格式** | 当前 JSONL v4 header 与 mutation 记录 | 独立的 JSONL v3 session header 与 entry 行 |
| **存储实现** | 内存仓储、`JsonlSessionRepo`，以及新 `session-backends` 包中的 `SqliteSessionRepository` | `SessionManager` 自己管理文件和索引 |

agent-core 的 `Entry` 联合类型只有 7 种；lane、记录和 name / label 都有自己的模型，name 与 label 是全会话 facts，不是 Entry。它的 v4 JSONL 还包含 `seq`、lane、record 等 mutation，与 coding-agent 的 v3 header 和 entry 行不是可直接替换的格式。coding-agent 的 `SessionManager` **既不实现 agent-core 的 `SessionStorage`，也不复用 agent-core 的 Entry 定义**。

两边对上下文的处理也有区别。coding-agent 的 `CompactionEntry` 用 `firstKeptEntryId` 从压缩边界前挑选保留 entry；agent-core 的 CompactionEntry 直接带 `retainedTail`，默认 context transform 会保留压缩节点和后续路径。agent-core 另有 `active_tools_change`，并允许通过 projector 把 `custom` entry 投影为上下文消息。

因此，`SessionStorage` / `SessionRepo` 给其他宿主提供了可替换后端的边界，但不要由此推断现成通用 harness 已经能完整运行 Agent：当前 `AgentHarness` 的 `prompt()`、`navigateTree()`、`resume()`、lane 操作等运行入口仍会返回 `HarnessNotImplemented`。这里看到的是逐步搭建中的通用会话与 harness 架构，不是 coding-agent `SessionManager` 换个数据库后即可直接复用。

> 实现：`packages/agent/src/harness/session/types.ts`（7 类 Entry、records、lanes、facts、SessionStorage / SessionRepo）；`packages/agent/src/harness/session/context.ts`（上下文投影）；`packages/agent/src/harness/session/jsonl/repo.ts`（`JsonlSessionRepo`、v4 JSONL 仓储）；`packages/session-backends/sqlite-node/src/sqlite/repo.ts`（`SqliteSessionRepository`）；`packages/agent/src/harness/agent-harness.ts`（尚未实现的运行入口）

## 八、总结

### 一条主线：会话存储的两个独立维度

回头看你能在这一章带走的最核心的东西——**会话数据怎么存，要拆成两个独立问题来想**：

| 维度 | 回答什么 | 一般做法 | Pi 的选择 |
|------|---------|---------|----------|
| **存储介质** | 存哪里？ | mysql 等数据库 | coding-agent 默认使用用户级目录中的 JSONL 文件 |
| **数据结构** | 长什么样？ | 线性数组 | 树（Session Tree） |

这两个维度可以独立做选择。下次你设计任何"对话历史持久化"或类似的状态保存系统，先问自己这两个问题，再决定方案——不要把它们粘成一团。

### Session Tree 的本质：用树形 + append-only 实现"不丢数据的回退"

为什么树？因为对话不是线性的——用户会回退、重试、分支。
为什么 append-only？因为删了的数据找不回来，而历史分支可能有价值。
为什么认父不认子？因为 append-only 要求节点不可变，父节点不能维护 children 列表。
为什么路径遍历？因为 LLM 只认线性 messages 数组，树形数据必须"压扁"。

**这一连串设计选择是连贯的**——每一个选择都回应了上一个选择带来的约束，最终形成一套自洽的方案。

### 三个可迁移的思路

**1. 拆开"存哪里"和"长什么样"两个维度。** 设计持久化系统时，先分别想清楚这两个问题，再组合方案。混在一起讨论会让选择空间被压缩——你会以为"用了数据库就必须线性数组"或"用了文件就必须 append-only"，其实不然。

**2. append-only 数据结构用于"撤销/回退/分支"场景。** 当系统需要这些能力时，不要删除旧数据。用 append-only + 指针定位（leafId），让历史完整保留。代价是存储空间，但磁盘便宜、数据无价。

**3. 节点化状态变量，让路径计算有据可依。** coding-agent 把"切换模型""调整思考级别"存成 entry；沿当前路径重算时，后续的 model_change 和 assistant message 会覆盖较早的模型记录。回退会改变参与计算的路径，但 UI 导航不会因此自动切换当前模型。
