前六章里，有一个东西反复出现但我们始终没深入——**事件**。

第 3 章说"Agent Loop 每做一步都发事件让 UI 实时更新"。第 5 章说"工具执行时发出 `tool_execution_start`、`tool_execution_update`、`tool_execution_end` 事件"。第 6 章里事件到处携带 `AgentMessage`。

但我们始终没回答：事件到底是怎么从 Agent 内部传到外部的？谁在监听？为什么 Agent 发完事件后对一类监听器"等"，对另一类"不等"？

这一章就打开 Agent 的"神经系统"。

> **本章最重要的一句话：Pi 至少要区分三种事件类型和两类消费入口。** 内核 `AgentEvent` 先驱动 Agent 状态与已等待的内核 listeners；`AgentSession` 再把它投影为扩展事件并通知 Session listeners。Session 自己还会产生队列、压缩、重试等事件；扩展系统也会在输入、工具决策和 Provider 请求等位置直接产生事件。`session.subscribe` 是同步通知监听器的只读观察入口，`pi.on` 则由扩展 Runner 按各事件方法的规则等待 handler，并在部分决策点读取返回值。

> 本章起为进阶章节。前六章建立了对 Pi-Agent 运行机制的整体理解，从这里开始深入工程化议题。

## 一、为什么需要事件系统？

### 一个直觉：从外卖追踪说起

你在美团上点了一份外卖。下单后，App 会给你推送一连串状态更新："商家已接单" → "骑手已取餐" → "骑手距你 500 米" → "已送达"。每一个状态更新就是一个**事件**——它告诉你"发生了一件事"。你不需要一直盯着骑手的位置看，只需要在收到事件时看一眼。

Pi-Agent 的事件就是这个意思：Agent 运行过程中不断产生"发生了某事"的快照——消息开始了、消息更新了、工具开始执行了——然后把这些快照推给所有关心它的人。

### 不用事件会怎样？

假设你要给 Agent 加一个"工具调用日志"功能：每次调工具时打印一行 `[LOG] 调用了 read，参数：main.ts`。

**不用事件系统**：你得改 Agent 源码，在 `tool.execute()` 前后各加一行 `console.log`。然后 Pi 更新了，你 merge 上游代码时发现冲突——你加的日志和上游新增的逻辑撞在一起了。手动解决冲突，下周又更新，又冲突……

**用事件系统**：

```typescript
session.subscribe((event) => {
    if (event.type === "tool_execution_end") {
        console.log(`[LOG] 调用了 ${event.toolName}，结果：${event.isError ? "失败" : "成功"}`);
    }
});
```

六行代码。不碰 Agent 一行源码。Agent 更新你只需要 `npm update`，日志逻辑不受影响。

这就是事件驱动最核心的价值：**把"发生了什么"和"谁关心什么"彻底分离。** Agent 只管发事件，它不知道也不关心谁在听。

### 发布-订阅 vs 直接调用

用编程术语说，事件驱动实现的是**发布-订阅模式**。和直接函数调用做个对比：

```
直接调用（打电话）：
  Agent ──调用──→ 终端渲染
       ──调用──→ 文件存储
       ──调用──→ 日志记录
  Agent 需要知道所有消费者的存在，每加一个新功能就要改 Agent

发布-订阅（广播）：
  Agent ──emit事件──→ 📡 事件总线
                          ├──→ 终端渲染（订阅了）
                          ├──→ 文件存储（订阅了）
                          ├──→ 日志记录（订阅了）
                          └──→ （新功能只需订阅，Agent 不需要知道）
```

一句话：**直接调用是"我亲自找你"；发布-订阅是"我对着空气喊了一声，谁听到算谁的"。** Pi 的事件系统就是发布-订阅——Agent 发出事件，关心它的人各自订阅、各自处理。但 Pi 有一个关键特点：**它有两条订阅管道**，而且两条的能力很不一样。这正是本章要讲的核心，下一节就铺开。

## 二、两条管道的全貌：从事件源到两类监听器

这一节把 Pi 事件体系的全景铺开——**2.1 看事件源，2.2 认识两条管道并讲清它们的核心差别**。后面第三、四节会分别深入两条管道的用法和源码。

### 2.1 事件源：10 种 AgentEvent

Agent 内核层定义了 10 种 `AgentEvent`，它们构成了 Agent 运行的完整"脉搏"：

<Diagram file="/assets/260702-ch07-event-nesting.svg" caption="10 种事件 4 层嵌套" id="260702-ch07-event-nesting" />

**配图说明**：Agent（Trace）包含多个 Turn；每个 Turn 中 Message 与 Tool Execution 是并列的事件族，不是互相嵌套。四组分别有 2、2、3、3 个事件类型，共 10 种 `AgentEvent`。

```typescript
export type AgentEvent =
  // 第1层：Agent 生命周期（整个运行）
  | { type: "agent_start" }
  | { type: "agent_end"; messages: AgentMessage[] }

  // 第2层：Turn 生命周期（一轮模型调用 + 工具执行）
  | { type: "turn_start" }
  | { type: "turn_end"; message: AgentMessage; toolResults: ToolResultMessage[] }

  // 第3层：Message 生命周期（一条消息）
  | { type: "message_start"; message: AgentMessage }
  | { type: "message_update"; message: AgentMessage; assistantMessageEvent: AssistantMessageEvent }
  | { type: "message_end"; message: AgentMessage }

  // 第4层：Tool Execution 生命周期（一次工具执行）
  | { type: "tool_execution_start"; toolCallId: string; toolName: string; args: any }
  | { type: "tool_execution_update"; toolCallId: string; toolName: string; args: any; partialResult: any }
  | { type: "tool_execution_end"; toolCallId: string; toolName: string; result: any; isError: boolean };
```

10 种看着不少，但规律很清楚——它们是 **4 层嵌套的生命周期**，每层都有"开始→更新→结束"的配对：

```
Agent 运行
├── agent_start ───────────────────── Agent 开始
│
├── Turn 1（第3章讲过：一次模型调用 + 它触发的工具执行）
│   ├── turn_start ────────────────── Turn 开始
│   │
│   ├── Message（LLM 的响应）
│   │   ├── message_start
│   │   ├── message_update ×N ────── 流式增量（逐 token 更新）
│   │   └── message_end
│   │
│   ├── Tool Execution（工具执行）
│   │   ├── tool_execution_start
│   │   ├── tool_execution_update ×N  工具进度（如 Bash 的输出）
│   │   └── tool_execution_end
│   │
│   └── turn_end ──────────────────── Turn 结束
│
├── Turn 2 ...
│
└── agent_end ──────────────────────── Agent 结束
```

回忆第 3 章的概念：**一个 Turn = 一次模型调用 + 这次调用触发的所有工具执行。** `turn_start` 到 `turn_end` 之间，模型被调用了恰好一次。Message 与 Tool Execution 都发生在 Turn 内，二者不是父子事件关系。

> `AgentEvent` 是内核事件联合类型，不是两类 listener 直接共享的一条总线。`AgentSession` 内部订阅 Agent 后才承担桥接：它先把内核事件转换为扩展事件并等待扩展派发，然后把对应的 `AgentSessionEvent` 同步通知 Session listeners。扩展还可以在 SDK 的决策点直接产生不对应内核事件的事件。

### 2.2 三种事件类型，两类消费入口

本章把两类常见消费入口简称为两条管道，但要先分清它们背后的事件类型和生产者：

| 层 | 类型与生产位置 | 作用 |
|---|---|---|
| Agent 内核 | `AgentEvent`，由 `packages/agent/src/types.ts` 定义 | 10 种运行时生命周期事件；`Agent.processEvents()` 先更新状态，再按顺序 `await` 内核 listeners |
| coding-agent Session | `AgentSessionEvent`，由 `packages/coding-agent/src/core/agent-session.ts` 定义 | 以 `AgentEvent` 为基础（`agent_end` 增加 `willRetry`），再加入队列、压缩、重试等产品层事件 |
| 扩展系统 | `ExtensionEvent`，由 `packages/coding-agent/src/core/extensions/types.ts` 定义 | 接收 `_emitExtensionEvent()` 投影的部分内核事件，也包括 SDK 在输入、工具决策、上下文和 Provider 生命周期等位置直接触发的事件 |

实际桥接顺序是：

```text
Agent Loop
  → Agent.processEvents(): 更新 AgentState，按注册顺序 await 内核 listeners
  → AgentSession._handleAgentEvent()
      → await _emitExtensionEvent(event) → ExtensionRunner 对应方法派发
      → _emit(AgentSessionEvent) → 同步调用 session.subscribe listeners
      → 持久化与 Session 自身后续处理
```

因此，`session.subscribe` 和 `pi.on` 不是从同一个事件总线上直接分出的两个消费者：普通内核事件由 `AgentSession` 适配后依次送往扩展和 Session listeners；Session 专属事件由 Session 自己发出；扩展专属决策事件则在 SDK 决策点直接调用 ExtensionRunner。

**入口 A：`session.subscribe`**

它注册 `AgentSessionEvent` listener，适合外部脚本、UI、日志和 SSE 等只读观察。Session 的 `_emit()` 会在当前调用栈里同步逐个调用 listener，不等待 listener 返回的 Promise，也不读取返回值。

**入口 B：扩展系统的 `pi.on`**

它注册扩展 handler。扩展 Runner 的方法会按各自实现等待 handler；工具拦截、上下文变换等方法还会读取返回值。不同 Runner 方法的错误捕获和返回值处理并不统一，后文按源码逐类说明。

<Diagram file="/assets/260702-ch07-two-pipelines.svg" caption="事件桥接与两类消费入口" id="260702-ch07-two-pipelines" />

**配图说明**：图中分开画出内核 `AgentEvent`、Session `AgentSessionEvent` 与扩展 `ExtensionEvent` 的生产和消费路径；内核事件经 `AgentSession` 先到扩展 Runner、再到 Session listeners，Session 专属事件和 SDK 决策事件则由各自位置产生。

**容易搞混的两个事件名：`tool_call` 与 `tool_execution_start`**

```text
LLM 返回一个 toolCall 内容块
   │
   ├─ Agent Loop 的 prepareToolCall() 调用 beforeToolCall hook
   │    → AgentSession 投影为 ExtensionEvent: tool_call
   │    → handler 可返回 block；该调用成为错误 ToolResult，不执行工具
   │
   └─ 通过准备阶段后才进入工具执行
        → AgentEvent: tool_execution_start
        → AgentSession 分别投影给扩展、再发给 Session listeners
```

`tool_call` 是扩展侧的执行前决策事件；`tool_execution_start` 是内核侧的执行生命周期事件。Session listener 收到后者，而不会收到 `tool_call`。除了 `tool_call`，`input`、`before_agent_start`、`context`、`tool_result` 等常见决策事件也由 SDK/Session 决策点触发；扩展事件类型还包括 Provider、Session、UI 与资源生命周期等其他类别，因此这五类不是全部扩展事件。

> **派发屏障按具体链路判断。** 核心 `Agent.subscribe` listener 被 `Agent.processEvents()` 按顺序 `await`；`AgentSession._handleAgentEvent()` 又先等待扩展投影，再同步调用 Session listeners。高频事件也沿这条等待链进入扩展 Runner，不能概括成“先缓冲、最后统一等待”。工具执行期间的进度事件如何排队或收尾，则由 Agent Loop 自己的工具更新逻辑决定。

## 三、管道 A：session.subscribe

2.2 介绍了管道 A 的特点：Agent 不等它，所以它只能看、不能改。这一节落到源码，看清"不等"和"只能看"是怎么实现的。

### 3.1 怎么用：注册、签名、注销

```typescript
// 注册：传入一个 listener，返回一个注销函数
const unsubscribe = session.subscribe((event) => {
    if (event.type === "message_update" && event.assistantMessageEvent.type === "text_delta") {
        process.stdout.write(event.assistantMessageEvent.delta);   // 流式打字
    }
});

// 不用了就调注销函数
unsubscribe();
```

listener 的签名是关键：

```typescript
type AgentSessionEventListener = (event: AgentSessionEvent) => void;
//                            注意：只有 event 参数；返回值类型为 void
```

listener 的类型只有一个 `AgentSessionEvent` 参数，返回类型写作 `void`。Session `_emit()` 同步调用它，不读取返回值；通过这个入口返回 `{ block: true }` 不会拦工具。这是只读观察接口的边界。

### 3.2 "不等"对管道 A 意味着什么

AgentSession 不等待 session.subscribe 监听器返回的 Promise。落到实战，这个"不等"带来三个直接后果：

- listener 的同步部分在 `_emit()` 的调用栈中运行，执行耗时会拖住当前事件派发。
- 如果 listener 返回 Promise，`_emit()` 不会等待它；异步结果不能用来影响 Agent 决策。
- `_emit()` 没有 `try/catch`：同步抛错会从 Session bridge 冒出并进入内核 listener 的错误处理路径；异步 Promise rejection 没有被 Pi 捕获，可能成为未处理拒绝。需要异步工作的 listener 应自行捕获并记录异常。

因此管道 A 适合只读观察、日志与事件转发，但必须意识到“Agent 不等 Promise”不等于“listener 完全不影响派发”：同步工作仍占用当前调用栈。

### 3.3 管道 A 能收到哪些事件

管道 A 收到的是 `AgentSessionEvent`，它比内核 10 种事件多出几个**产品级事件**——这些事件反映的不是"Agent 内核跑了一步"，而是"产品层做了某件事"（压缩、重试、排队等）。内核根本不知道这些概念，所以它们只出现在产品层。

大致有个印象就行，遇到具体场景再查：

| 事件 | 什么时候触发 | 典型用途 |
|------|------------|---------|
| `agent_settled` | 一次 `prompt()` 彻底跑完（含重试/压缩/队列全部处理完） | 可靠的结束信号：写库收尾、推 SSE done |
| `compaction_start` / `compaction_end` | 上下文窗口快满时，自动压缩历史（第9章详讲） | UI 显示"正在压缩..."提示 |
| `auto_retry_start` / `auto_retry_end` | Session 对满足配置条件的可重试错误执行自动重试时 | UI 显示重试次数、告警 |
| `queue_update` | steering / followUp 消息队列变化 | UI 更新"排队中"状态 |
| `session_info_changed` | 会话名称等元信息变化 | UI 刷新标题 |
| `thinking_level_changed` | 切换思考深度 | UI 联动显示 |

`AgentSessionEvent` 的内核部分以 `AgentEvent` 为基础，其中 `agent_end` 会增加 `willRetry` 信息；再加上上表所列 Session 事件。它不是“10 种内核事件加几个”的简单计数，完整联合类型应以源码定义为准。

管道 A 收不到扩展专属的 `input`、`before_agent_start`、`context`、`tool_call`、`tool_result` 等事件，因为它监听的是 `AgentSessionEvent`。扩展事件还包括 Provider、Session、UI 与资源生命周期事件。

### 3.4 什么时候用管道 A

一句话：**纯观察、不改 Agent 行为、不需要 Agent 等你的场景。** 典型用途——流式渲染（TUI 逐 token 打字）、日志记录、SSE 转发给浏览器、统计 token 用量。这些场景的共同点是"Agent 干它的，我在旁边看一眼、或慢慢做我自己的事"，不需要 Agent 配合。

> 💡 **落库 / 审计 / 日志通常属于只读观察**，可由管道 A 接收事件后转发给自己的队列。要注意 `_emit()` 会同步调用 listener；异步写库 Promise 不会被等待或捕获，可靠持久化需要你自己的队列、错误记录和关闭时 flush 机制。
>
> 如果数据必须在 `tool_call` / `tool_result` / `context` 等扩展事件上采集，需从扩展入口获取。扩展 handler 是否被等待、异常如何处理，取决于具体 ExtensionRunner 方法；若只做后台 I/O，可将任务交给应用自有 worker 后尽快返回。
>
> 一个易踩的坑：`message_end` 看着像"一条消息存一笔"的好时机，但它一轮 `prompt()` 会触发多次（每条 assistant 消息结束都发，含中间要调工具的那些）。拿它当整轮收尾会重复落库 / 重复推 done。整轮的可靠收尾用 `agent_settled`——它每 prompt 只发一次。

## 四、管道 B：扩展系统 pi.on

这一节是本章的重头戏。管道 B 的能力远超管道 A——它能拦截工具、改写上下文、替换系统提示词。这些能力的源头，是 SDK 在关键决策点**停下来等扩展的返回值**（2.2 讲的"Agent 等"）。

### 4.1 怎么用：写扩展、挂载、注册

管道 B 的代码不在"外部脚本"里，而是写在**扩展**里——一个接收 `pi` 对象的工厂函数：

```typescript
// 一个扩展：框架启动时调它，把遥控器 pi 传进来
function myGuardExtension(pi) {
    // 用 pi.on 盯住"工具调用前"这个事件
    pi.on("tool_call", async (event, ctx) => {
        if (event.toolName === "delete_table") {
            return { block: true, reason: "生产环境禁止删除操作" };   // ← 有返回值，能拦
        }
        return undefined;   // 放行
    });
}
```

挂载通过 `DefaultResourceLoader` 的 `extensionFactories`：

```typescript
const loader = new DefaultResourceLoader({
    cwd: process.cwd(),
    agentDir: getAgentDir(),
    extensionFactories: [myGuardExtension],   // ← 你的扩展塞这儿
});
await loader.reload();

const { session } = await createAgentSession({ /* ..., */ resourceLoader: loader });
```

注意两个关键点：
- **handler 有返回值**（`return { block: true }`）——这是管道 B 能干预 Agent 的根本，也是"Agent 必须等你"的原因（要读返回值）。
- **handler 多一个 `ctx` 参数**——扩展上下文，能力比管道 A 的 `event + signal` 强（见 4.4）。

### 4.2 源码：pi.on 只是往 Map 里 push

管道 B 的注册实现极简。`pi.on` 做的事就是往一个 Map 里塞 handler：

```typescript
// packages/coding-agent/src/core/extensions/loader.ts · createExtensionAPI()
const api = {
    on(event: string, handler: HandlerFn): void {
        runtime.assertActive();
        const list = extension.handlers.get(event) ?? [];
        list.push(handler);
        extension.handlers.set(event, list);
    },
};
```

每个扩展对象内部有一个 `handlers: Map<事件名, handler[]>`。`pi.on("tool_call", h)` 就是在 `"tool_call"` 这个 key 下追加 `h`。派发时遍历这个 Map。

### 4.3 源码：extensionRunner 的两条派发路径

真正的差别在派发。ExtensionRunner 暴露多种方法；下面以通知型 `emit()`、决策型 `emitToolCall()` 和链式 transform 方法为例。它们都会等待 handler，但是否读取返回值、如何捕获错误都由具体方法决定：

**路径 1：通知型 `emit()`（`packages/coding-agent/src/core/extensions/runner.ts` · `emit()`）**——处理部分 `message_update`、`turn_start` 等事件：

```typescript
class ExtensionRunner {
    async emit<TEvent extends RunnerEmitEvent>(event: TEvent): Promise<RunnerEmitResult<TEvent>> {
        const ctx = this.createContext();
        let result: SessionBeforeEventResult | undefined;
        for (const ext of this.extensions) {
            const handlers = ext.handlers.get(event.type);
            if (!handlers || handlers.length === 0) continue;
            for (const handler of handlers) {
                try {
                    const handlerResult = await handler(event, ctx);
                    // 普通通知忽略返回值；session_before_* 会读取 cancel。
                    if (this.isSessionBeforeEvent(event) && handlerResult?.cancel) {
                        return handlerResult;
                    }
                } catch (err) {
                    const message = err instanceof Error ? err.message : String(err);
                    const stack = err instanceof Error ? err.stack : undefined;
                    this.emitError({ extensionPath: ext.path, event: event.type, error: message, stack });
                }
            }
        }
        return result as RunnerEmitResult<TEvent>;
    }
}
```

特征：**按扩展与 handler 注册顺序 await；每个 handler 单独 try-catch，失败通过 `emitError` 报告后继续；普通通知事件忽略返回值**。对于四种 `session_before_*` 事件，`emit()` 会读取 `{ cancel }` 并可提前返回。`AgentSession` 在等待该方法结束后才发 Session event，因此扩展通知 handler 会形成这条 bridge 的屏障。`_emitExtensionEvent()` 只投影部分内核事件，不是全部 `AgentEvent` 都一对一转换。

**路径 2：决策型 `emitToolCall()`（`packages/coding-agent/src/core/extensions/runner.ts` · `emitToolCall()`）**——处理 `tool_call` 拦截：

```typescript
class ExtensionRunner {
    async emitToolCall(event: ToolCallEvent): Promise<ToolCallEventResult | undefined> {
        const ctx = this.createContext();
        let result: ToolCallEventResult | undefined;
        for (const ext of this.extensions) {
            const handlers = ext.handlers.get("tool_call");
            if (!handlers || handlers.length === 0) continue;
            for (const handler of handlers) {
                const handlerResult = await handler(event, ctx);
                if (!handlerResult) continue;
                result = handlerResult;
                if (result.block) return result;
            }
        }
        return result;
    }
}
```

特征：**await + 读返回值 + `block` 短路 + 本方法不做逐 handler try-catch**。handler 抛错会从 `emitToolCall()` 冒出，经 `AgentSession.beforeToolCall` 返回到 `prepareToolCall()`；Loop 将该调用整理为错误 ToolResult，跳过实际工具执行，再把结果交回模型。不能把它概括成“Runner 统一 fail-closed”：此路径的异常如何影响后续运行由调用方处理。

**路径 3：链式 transform 型**——还有一批决策事件走"链式 transform"，每个 handler 接收上一个的输出继续改。比如：

- `emitContext()`（runner.ts:979）：第一个 handler 拿到原始 messages，改完传给第二个，最后一个的输出就是真正发给 LLM 的消息列表。返回类型 `AgentMessage[]`。
- `emitToolResult()`（runner.ts:872）：链式修改工具结果，返回 `ToolResultEventResult`。
- `emitBeforeAgentStart()`（runner.ts:1076）：链式覆盖系统提示词 + 收集注入消息。
- `emitInput()`（runner.ts:1191）：链式改写用户输入，`action: "handled"` 短路。

这些 transform 方法会等待 handler、按各自类型合并返回值；例如 `emitContext()` 捕获单个 handler 异常、报告 `emitError` 后继续处理。`emitMessageEnd()`、`emitToolResult()`、`emitBeforeAgentStart()`、`emitInput()` 与 Provider 相关方法也有各自错误处理，具体返回值、短路和继续策略不完全相同。应按实际调用方法判断，不能把“所有扩展 handler 都隔离”当作通用规则。

### 4.4 ctx：扩展上下文

handler 签名 `(event, ctx)` 里的 `ctx` 是 `ExtensionContext`，能力远强于管道 A 的 `event + signal`：

```typescript
interface ExtensionContext {
    ui: ExtensionUIContext;
    mode: "tui" | "rpc" | "json" | "print";
    cwd: string;
    sessionManager: ReadonlySessionManager;
    modelRegistry: ModelRegistry;
    model: Model<any> | undefined;
    thinkingLevel: ThinkingLevel | undefined;
    signal: AbortSignal | undefined;
    abort(): void;
    isIdle(): boolean;
    compact(options?: CompactionOptions): void;
    getSystemPrompt(): string;
    getContextUsage(): ContextUsage | undefined;
    hasPendingMessages(): boolean;
}
```

一个**容易踩的坑**：`sessionManager` 是 `ReadonlySessionManager`——能读会话历史（`getEntries()`），但**不能直接写**。扩展要写 session 得走 `pi.sendMessage()` / `pi.appendEntry()` 等 action 方法，或在命令上下文（`ExtensionCommandContext`，能力更全）里操作。

### 4.5 扩展独占事件的触发位置

管道 B 独占的事件（包括 5 个决策点，以及 provider 类事件），都不在 `_emitExtensionEvent` 的翻译列表里（2.2 提到，那个方法只翻译 2.1 的流式生命周期事件），而是 SDK 在**各自的决策点**主动调用的。它们的触发位置分布在两个文件：

| 扩展独占事件 | 触发位置 | 挂在哪个内核 hook 上 |
|---|---|---|
| `tool_call`（执行前）| `agent-session.ts` | `agent.beforeToolCall` |
| `tool_result`（执行后）| `agent-session.ts` | `agent.afterToolCall` |
| `input`（用户输入后）| `agent-session.ts` | `sendUserMessage` 流程，skill/template 展开前 |
| `before_agent_start`（开跑前）| `agent-session.ts` | `sendUserMessage` 流程，`agent.run` 前 |
| `context`（发 LLM 前）| `sdk.ts` | `agent.transformContext` |
| `before_provider_request`（HTTP 发出前）| `sdk.ts` | `onPayload` 回调 |
| `after_provider_response`（收到响应）| `sdk.ts` | `onResponse` 回调 |

这些例子说明扩展事件有多个生产位置：有些挂在 Agent hook 上，由 `AgentSession` 适配；`context` 与 Provider hooks 在 SDK 的模型调用链中触发；Session、UI 与资源类事件又有各自的调用方。管道 A 监听 `AgentSessionEvent`，因此不会收到这些 ExtensionEvent。

### 4.6 什么时候用管道 B

一句话：**需要改变 Agent 行为的场景。** 拦截危险工具调用、改写发给 LLM 的上下文、替换系统提示词、修改工具返回值、过滤用户输入——这些"干预"类需求，管道 A 做不到（不等你就意味着返回值丢弃），只能写扩展走管道 B。

## 五、实战：四个场景，各走哪条管道

理解了两条管道的机制，就能判断每个需求该用哪条。下面四个场景覆盖最常见的集成需求，**按管道分组**——这是本章最重要的实战判断。

### 5.1 管道 A 实战组（session.subscribe，只读观察、Agent 不等）

#### 场景1：实时观测 Agent 在干什么

```typescript
session.subscribe((event) => {
    if (event.type === "tool_execution_start") {
        console.log(`🔧 ${event.toolName}(${JSON.stringify(event.args).slice(0, 50)})`);
    }
    if (event.type === "tool_execution_end") {
        console.log(`   └─ ${event.isError ? "❌ 失败" : "✅ 成功"}`);
    }
});
```

**为什么走管道 A**：纯观察，不改变 Agent 行为。Agent 不等你也无所谓——你要做的只是"看到事件、打印一行"，同步即可完成。Pi 的 TUI 本身就是通过订阅事件实现的观测面板——你看到的所有终端输出都来自管道 A 的消费。

#### 场景2：流式转发到 Web 前端（SSE）

```typescript
// 服务端
session.subscribe((event) => {
    if (event.type === "message_update") {
        res.write(`data: ${JSON.stringify({ type: "delta", text: extractText(event.message) })}\n\n`);
    }
    if (event.type === "agent_end") {
        res.end();
    }
});
```

**为什么走管道 A**：纯转发，不改 Agent。Agent 运行在服务器上，用户通过浏览器访问，订阅事件流通过 SSE 推给浏览器——这就是 Web 集成的核心。

### 5.2 管道 B 实战组（扩展 pi.on，能干预、Agent 等你）

#### 场景3：工具调用拦截

```typescript
function guardExtension(pi) {
    pi.on("tool_call", async (event) => {
        if (event.toolName === "delete_table") {
            return { block: true, reason: "生产环境禁止删除操作" };
        }
        return undefined;   // 放行
    });
}
// 挂载：extensionFactories: [guardExtension]
```

**为什么必须走管道 B**：要拦截、要返回 `{ block: true }`——管道 A 的 listener 不被等、返回值被丢弃，根本拦不住。而且 `tool_call` 这个事件**只在管道 B 派发**，管道 A 收不到。第 5 章讲的五步管道中第 3 步 `beforeToolCall`，底层就是这条管道实现的。

#### 场景4：上下文预处理

```typescript
function contextExtension(pi) {
    pi.on("context", async (event) => {
        // 在 LLM 调用前，往消息列表里注入当前时间
        return { messages: [{ role: "user", content: `当前时间：${new Date()}` }, ...event.messages] };
    });
}
```

**为什么必须走管道 B**：要改写发给 LLM 的消息列表——这是"改变 Agent 行为"，必须返回新列表让 Agent 采用（Agent 会等你返回）。第 6 章讲的 `transformContext` 钩子是同一条管道的实现（内核层的 `transformContext` 配置项和扩展层的 `context` hook 是同一件事的两面，一个走配置、一个走扩展）。

### 5.3 怎么选管道？一句话判断

> **你的代码要不要改变 Agent 的行为？**
> - 要（拦截、改参数、改消息、存状态）→ 写扩展，走**管道 B（`pi.on`）**。Agent 会等你、读你的返回值。
> - 不要（打日志、推前端、记统计）→ 用 **管道 A（`subscribe`）** 更轻。Agent 不等你、不读返回值。

### 5.4 小结

这四个场景的共同点是：**都不需要修改 Agent 内核。** 无论走哪条管道，新增功能都只是"挂一段自己的代码"。

事件驱动架构的真正威力不是"通知机制"（那只是管道 A），而是**开放扩展机制**——尤其是管道 B，它让第三方在不碰内核源码的前提下，能拦截、能改写、能干预。两条管道合起来，才构成 Pi 完整的"神经系统"。

## 六、总结：两条管道

Pi 的事件系统要区分具体入口：**核心 Agent.subscribe 会等待 listener；session.subscribe 只同步通知，不等待 Promise；扩展 handler 的等待与结果消费由对应 emitter 规定。**

**管道 A（`session.subscribe`）** —— Session `_emit()` 同步调用 listener，不读取其返回值，也不等待返回的 Promise；同步工作仍在当前调用栈，异步拒绝由调用方自行捕获和记录。

**管道 B（扩展 `pi.on`）** —— ExtensionRunner 各方法等待 handler；工具拦截、上下文变换等方法会读取返回值。扩展事件的生产者不只 AgentSession bridge，还包括输入、Session、UI、资源与 Provider 决策点。不同派发方法有不同异常策略：`emit()` 和多种 transform 方法会捕获并报告；`emitToolCall()` 不做逐 handler 捕获，错误沿调用链进入 `prepareToolCall()`，成为不执行工具的错误 ToolResult。

判断用哪条管道，只问一句：**你的代码是否需要参与宿主决策**——需要时选择有对应结果协议的扩展事件；观察 Session 时可用 session.subscribe，并自行管理异步任务。这里的“只读观察”描述入口职责，不表示事件对象被冻结；返回值不会作为拦截结果被读取。

## 七、下一站

本章我们看到，事件系统把 Agent 内核、coding-agent Session 与扩展系统连接起来。`AgentEvent`、`AgentSessionEvent` 和 `ExtensionEvent` 各有生产者与消费者；`session.subscribe` 与 `pi.on` 分别提供 Session 观察和扩展处理入口，具体等待、返回值与错误规则由对应派发实现决定。

但有一个和事件密切相关的机制我们只提了一句：**`transformContext`**（管道 B 的 `context` hook 在内核层的对应物）。第 6 章讲消息系统时说它在 `convertToLlm` 之前执行，负责裁剪旧消息、注入外部上下文。当对话越来越长，消息越来越多，最终会超出模型的上下文窗口。这时候 `transformContext` 需要做一件更激进的事——**压缩对话历史**。
