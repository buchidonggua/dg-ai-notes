第 3 章我们追踪了 Agent Loop 的完整运转过程。其中最关键的一步是"调用模型"——Loop 把消息发给 LLM，拿到回复，根据回复决定继续还是停止。

但当时我们用了一行代码就跳过了：

```python
# ============================================================
# 【Python改写】统一流函数调用
# 概念对照（Python 中对应为调用接收模型、上下文和可选选项的流式函数。）
# 原文 TS（完整节选，逐行注释）：
# const stream = streamFn(model, context, options);
# ============================================================
# 教学示意：统一流式调用；非官方 Python SDK。
stream = stream_fn(model, context, options)
```

这行代码看起来平平无奇。`streamFn` 是注入循环的模型调用函数，宿主可以把 `models.streamSimple.bind(models)` 交给它，也可以提供自己的实现。打开 `packages/ai/src/api/`，你会发现大量协议实现与公共辅助文件；当前 `KnownApi` 列出 10 种对话 API，图片生成另有 `KnownImagesApi`。**一行调用的简洁背后，是整个 AI 抽象层的设计。**

这一章就来拆开这一行代码：Pi 怎么做到用同一个接口调用 30 多个不同的模型？如果你想接入一个新模型，需要做什么？

---

## 一、问题：同一段对话，不同模型要"翻译"成不同格式

先说清楚要解决什么问题。

Agent Loop 要调用模型，但市面上有几十家模型供应商——Anthropic（Claude）、OpenAI（GPT）、Google（Gemini）、AWS Bedrock、Mistral……每家都有自己的 API 规范，用不同的字段名、不同的数据结构来描述同一件事情。

这个差异有多大？我们看一个最简单的例子。假设用户对 Agent 说了一句话：

> "帮我读一下 main.ts"

这条消息在 Pi 内部是这样存的（统一格式）：

```python
# ============================================================
# 【Python改写】统一消息结构
# 概念对照（统一上下文先保存 Pi 自己的规范化消息；时间戳是消息元数据。）
# 原文 TS（完整节选，逐行注释）：
# { role: "user", content: "帮我读一下 main.ts", timestamp: 1748697600000 }
# ============================================================
# 教学示意：内部统一消息使用普通映射表达；非官方 Python SDK。
message = {"role": "user", "content": "帮我读一下 main.ts", "timestamp": 1748697600000}
```

但要把这条消息发给不同模型，就必须"翻译"成各家要求的格式。同样是这一句话，四个 Provider 要求的长相完全不同：

**Anthropic（Claude）**——消息内容必须是数组，每项带 `type` 字段：

```python
# ============================================================
# 【Python改写】Anthropic 消息适配
# 概念对照（适配层把统一文本转换为 Anthropic 的内容块列表，并添加 type。）
# 原文 TS（完整节选，逐行注释）：
# { role: "user", content: [{ type: "text", text: "帮我读一下 main.ts" }] }
# ============================================================
# 教学示意：转换为 Anthropic 风格的文本块结构；非官方 Python SDK。
anthropic_message = {
    "role": "user",
    "content": [{"type": "text", "text": "帮我读一下 main.ts"}],
}
```

**OpenAI（GPT）**——格式看起来差不多，但字段语义有细微差异（比如工具结果消息的处理方式完全不同）：

```python
# ============================================================
# 【Python改写】OpenAI 消息适配
# 概念对照（文本用户消息的外形接近统一格式；存在工具结果时，适配层需按 OpenAI 的独立 tool 消息规则转换。）
# 原文 TS（完整节选，逐行注释）：
# { role: "user", content: "帮我读一下 main.ts" }
# // 但如果消息里包含工具结果，OpenAI 要求单独的 { role: "tool" } 消息，
# // 而 Anthropic 把工具结果合并到 user 消息里
# ============================================================
# 教学示意：OpenAI 兼容消息形状；工具结果需另转成 role=tool 消息。
openai_messages = [
    {"role": "user", "content": "帮我读一下 main.ts"},
]
```

**Google（Gemini）**——字段名从 `content` 变成了 `parts`，结构更扁平：

```python
# ============================================================
# 【Python改写】Google 消息适配
# 概念对照（Google 风格把内容字段放在 parts 中。）
# 原文 TS（完整节选，逐行注释）：
# { role: "user", parts: [{ text: "帮我读一下 main.ts" }] }
# ============================================================
# 教学示意：Google 风格把消息内容放在 parts 中。
google_message = {
    "role": "user",
    "parts": [{"text": "帮我读一下 main.ts"}],
}
```

**Bedrock（AWS）**——在 AWS 自己的结构上又包了一层：

```python
# ============================================================
# 【Python改写】Bedrock 消息适配
# 概念对照（Bedrock 的结构也使用内容块，但 text 项没有 Anthropic 的 type 字段。）
# 原文 TS（完整节选，逐行注释）：
# { role: "user", content: [{ text: "帮我读一下 main.ts" }] }
# // 注意：Bedrock 的 text 没有 type 字段，和 Anthropic 不一样
# ============================================================
# 教学示意：Bedrock 内容块不包含 Anthropic 的 type 字段。
bedrock_message = {
    "role": "user",
    "content": [{"text": "帮我读一下 main.ts"}],
}
```

**连最简单的纯文本消息都有四种写法。** 字段名不同（`content` vs `parts`），结构不同（有的要 `type` 字段，有的不要）。

<Diagram file="/assets/260702-ch04-provider-formats.svg" caption="四个 Provider 的消息格式差异" id="260702-ch04-provider-formats" />

**配图说明**：顶部是 Pi 内部统一格式，下面四个并排列出同一条消息在 Anthropic/OpenAI/Google/Bedrock 下的真实长相。每张卡片底部用红色标出"这家独特的地方"——数组+type、独立 role、parts 替换 content、无 type 等。底部还列出四个差异维度的全景。

### 不只是消息格式——四个维度全都不一样

消息格式只是冰山一角。Provider 之间的差异是全方位的，主要在四个维度上：

| 维度 | 差在哪 | 举个例子 |
|------|--------|---------|
| **消息格式** | 同一条消息，字段名和结构不同 | Anthropic 用 `content[]`，Google 用 `parts[]` |
| **流式传输** | 模型的"逐字返回"机制不同 | Anthropic 用 SDK 的 `asResponse()` 取得响应后自行解析 SSE，OpenAI SDK 返回结构化 chunk |
| **思考模式** | "让模型深度思考"的参数完全不同 | Anthropic 用 `thinking.budget_tokens`，OpenAI 用 `reasoning_effort` |
| **缓存控制** | "标记不变内容"的方式不同 | Anthropic 打 `cache_control` 标记，Bedrock 插入 `cachePoint` 节点 |

每个维度单独看都不复杂，但四个维度乘以 30 多个 Provider，组合起来的差异量是巨大的。

现在问题来了：**Agent Loop 只调用注入的 `streamFn(model, context)`，它不可能为每个 Provider 写一套不同的逻辑。那它怎么应对这么多差异？**

---

## 二、解法：三层架构，各管一件事

你可能会想到一个直觉的答案：给所有 Provider 做一层封装，让它们看起来都一样——输入相同、输出相同。

**没错，Pi 正是这么做的。** 但具体怎么"让它们看起来都一样"？Pi 的方案是把这件事拆成三层，每层有明确的分工：

```
第一层 · 统一入口    →  "接收请求，查出该找谁处理"
第二层 · 事件协议    →  "约定输出格式——不管谁处理，交回来的都是这个样子"
第三层 · 翻译器      →  "真正干活的人——每个翻译器精通一种 Provider 的方言"
```

用一个类比来理解。想象一个国际翻译公司：

- **第一层（前台）**：客户进门，前台问"你要翻译什么语言？"，然后查通讯录找到对应的翻译员，把工作派给他
- **第二层（标准报告模板）**：不管翻译员翻译的是法语、日语还是阿拉伯语，最终交出来的报告都必须用公司统一的格式——封面、正文、审签栏，格式固定
- **第三层（翻译员们）**：每个翻译员精通一种语言，内部怎么翻译是他们的事，但输出必须符合第二层的标准格式

**关键点：前台（第一层）和翻译员（第三层）之间靠标准报告（第二层）连接。前台不需要懂外语，翻译员不需要懂公司流程。**

Agent Loop 就是那个"客户"——它把请求交给前台（第一层），拿到标准格式的报告（第二层），从不直接接触翻译员（第三层）。

<Diagram file="/assets/260702-ch04-translation-company.svg" caption="翻译公司三层架构" id="260702-ch04-translation-company" />

**配图说明**：从上到下四层——客户（Agent Loop）→ 前台（Models，按 `model.provider` 找 Provider、准备认证，再按 `model.api` 派发）→ 标准报告协议（12 种事件）→ 翻译员们（4 种 API 的代表）。各 API 实现最终都把响应映射为统一事件流，返回给 Agent Loop。

下面逐层展开。

### 第一层：统一入口

如果沿当前 SDK 的实例入口走，前台是 `createModels()` 创建的 **Models 集合**。先把 Provider 放进去，再取模型、发请求：

```python
# ============================================================
# 【Python改写】创建模型集合并注册 Provider
# 概念对照（实例化 Models 集合，注册 Provider，再按 provider id 与 model id 取模型。）
# 原文 TS（完整节选，逐行注释）：
# import { createModels } from "@earendil-works/pi-ai";
# import { anthropicProvider } from "@earendil-works/pi-ai/providers/anthropic";
#
# const models = createModels();
# models.setProvider(anthropicProvider());
# const model = models.getModel("anthropic", "claude-sonnet-4-6");
# if (!model) throw new Error("Model not found");
# ============================================================
# 教学示意：实例化集合、注册 Provider 并取模型；非官方 Python SDK。
models = create_models()
models.set_provider(anthropic_provider())
model = models.get_model("anthropic", "claude-sonnet-4-6")
if model is None:
    raise LookupError("Model not found")
```

这里有两个“工号”，不能混在一起：

| 字段 | 回答什么问题 | 示例 |
|------|-------------|------|
| `model.provider` | 请求属于哪家服务、用哪套认证？ | `anthropic`、`openrouter` |
| `model.api` | 使用什么请求与响应协议？ | `anthropic-messages`、`openai-completions` |

`ModelsImpl.streamSimple()` 先用 `model.provider` 找到 Provider，再由 `applyAuth()` 解析认证、合并请求 headers / env，必要时用认证结果里的 baseUrl 更新请求模型；随后才交给 Provider 的 `streamSimple()`。`createProvider()` 组装的 Provider 再按 `model.api` 选择 API 实现。

```
Models.streamSimple(model, context, options)
    → requireProvider(model.provider)    按服务 ID 找 Provider
    → applyAuth(model, options)          解析认证并准备请求配置
    → provider.streamSimple(...)         委派给这个 Provider
    → createProvider 按 model.api 选择 API
    → API.streamSimple(...)              翻译通用选项并发起流式请求
```

这解释了为什么“提供商”和“翻译器”不是一对一：两家不同的服务都可以说 OpenAI Completions 这门“方言”，共享协议实现，却使用各自的地址、认证和模型目录。

还有一个时序细节：认证解析是异步的，但 `models.streamSimple()` **立即返回事件流对象**。它通过 `lazyStream()` 在流后面做异步准备，成功后转发内部事件，准备失败则发送 `error` 并结束流。前台不只是查表，它也负责把异步准备接到统一的流接口上。

### 旧的全局入口去哪了？

如果你从 coding-agent 的压缩代码或旧例子进入，仍然会看到全局 `streamSimple()`。它在明确的子入口里：

```python
# ============================================================
# 【Python改写】导入兼容入口
# 概念对照（仍可从兼容子模块使用旧的全局入口；Python 名称仅作概念对照。）
# 原文 TS（完整节选，逐行注释）：
# import { getModel, streamSimple } from "@earendil-works/pi-ai/compat";
# ============================================================
# 教学示意：旧兼容入口集中在子模块；非官方 Python SDK。
from pi_ai.compat import get_model, stream_simple
```

`compat.ts` 会注册 `BUILTIN_APIS`，保留 `registerApiProvider()` 等全局 API。当前它的调用也不只是“按 api 查表”：内置 Provider 适用时先走内置 Provider 的流方法；否则才用 `resolveApiProvider(model.api)` 找全局注册项，特定认证路径还会委托给内部 Models 集合。

**两条入口是并存的，不能把其中一条写成所有调用都必经的路线。** 本章以实例入口解释职责，再在源码索引标出兼容路径。第 2 章的 `streamFn` 注入让 Agent Loop 能使用其中任意一种，而不需要把注册表逻辑写进循环。

### 第二层：事件协议

翻译器把请求发给模型后，模型会流式返回内容（一个字一个字地"吐"出来）。如果每个翻译员都按自己的方式吐，前台就疯了。所以第二层约定了一套统一的输出格式。

Pi 规定：不管底层是哪家模型，翻译器都必须输出**统一的事件流**，事件类型一共 12 种：

```
AssistantMessageEvent（12 种）
│
├── start                              ← 流开始了
│
├── text_start → text_delta → ... → text_end       ← 模型在输出文字
├── thinking_start → thinking_delta → ... → thinking_end  ← 模型在思考
├── toolcall_start → toolcall_delta → ... → toolcall_end  ← 模型要调工具
│
├── done   (reason: stop / length / toolUse / deferred) ← 返回最终结果或延期句柄
└── error  (reason: error / aborted)           ← 出错了
```

你不需要记住全部 12 种。只需要理解模式：**模型回复的内容分三类（文字、思考、工具调用），每类都有"开始→逐字增量→结束"三步，再加上流开始和流结束两个信号。**

每类内容为什么是三步？因为这是流式输出——翻译器先告诉你"文字要开始了"（text_start），然后逐字推送（text_delta，可能有很多个），最后告诉你"文字结束了"（text_end）。这样 Agent Loop 可以做到逐字渲染——你看到的 AI 回复一个字一个字蹦出来，就是这个机制。

还有一个重要约定：`start` 和文字、思考、工具调用的过程事件携带 `partial: AssistantMessage`——当前消息的完整快照。第 3 章讲的“原地替换”就是消费这些过程快照；终止事件另有字段，`done` 带 `message`，`error` 带 `error`，不能统一读取 `event.partial`。

`deferred` 没有增加第 13 种事件，它是 `done.reason` 的一种值：服务端接受了任务，结果需要稍后获取，消息里可以携带 `DeferredHandle`。Models 提供 `fetchDeferred()` / `cancelDeferred()`，但要看 Provider 是否实现对应能力；这不等于 Agent Loop 自动具备持久化挂起和恢复机制。

### 第三层：翻译器

翻译器是真正干活的角色。每个翻译器对应一种 API（如 Anthropic、OpenAI），负责把统一格式翻译成该 Provider 的私有格式，再把响应翻译回统一事件。

对普通流式对话请求，可以把翻译器的工作归纳为 5 步：

<Diagram file="/assets/260702-ch04-translator-5-steps.svg" caption="翻译器内部 5 步骨架" id="260702-ch04-translator-5-steps" />

**配图说明**：垂直 5 步管道——创建客户端→构建请求参数→发送请求→处理响应流→发送终止事件。第 2 步和第 4 步是工作量所在（红色边框高亮）。右侧失败分支汇聚成统一 error 事件。

```
翻译器(model, context, options)
│
├── 1. 创建客户端
│      用 API Key 初始化连接。就像翻译员确认自己带了字典。
│
├── 2. 构建请求参数
│      把统一格式的消息、工具定义、系统提示，翻译成 Provider 的私有格式。
│      比如 Google 要 content → parts，这一步就做这个转换。
│
├── 3. 发送请求
│      通过 SDK 或直接 HTTP 发给模型。等模型开始响应。
│
├── 4. 处理响应流
│      模型流式返回内容。翻译器把 Provider 的私有事件格式，
│      翻译成第二层要求的 12 种统一事件。
│
└── 5. 发送终止事件
       成功 → push done；失败 → push error。流必须终止。
```

第 2 步（请求翻译）和第 4 步（响应翻译）是重点阅读位置。5 步是帮助我们阅读的归纳，不代表每个 API 都有相同函数划分；懒加载、认证和部分公共参数处理已经在外围完成。

以 Anthropic 为例，第 4 步的翻译规则（把 Anthropic 的私有事件名翻译成 Pi 的统一事件名）：

```
Anthropic 私有事件                     →  Pi 统一事件
─────────────────                    ────────────
content_block_start (type: "text")    →  text_start
content_block_delta (text_delta)      →  text_delta
content_block_start (type: "tool_use") →  toolcall_start
content_block_delta (input_json)      →  toolcall_delta
message_delta (stop_reason)           →  更新 output.stopReason
整个响应流结束                         →  done（携带完整 output）
```

注意终止原因的映射：Anthropic 的 `"end_turn"` → Pi 的 `"stop"`，`"tool_use"` → `"toolUse"`。每个 Provider 的命名都不一样，Pi 统一成了自己的术语。第 3 章讲 Agent Loop 检查 `stopReason` 决定是否继续循环，那些值就是经过这层翻译后的统一术语。

### StreamFunction：翻译器的"入职要求"

前面说的三层架构要运转起来，有一个前提：**所有翻译器必须遵守同一套规则。** Pi 用一个 TypeScript 类型来定义这套规则——它叫 `StreamFunction`，是整个抽象层的"宪法"：

```python
# ============================================================
# 【Python改写】流函数协议
# 概念对照（Python 的 Protocol 可描述调用签名，AsyncIterator 表示异步事件序列；对应类型关系而非官方接口。）
# 原文 TS（完整节选，逐行注释）：
# export type StreamFunction<TApi extends Api, TOptions> = (
#   model: Model<TApi>,       // 用哪个模型
#   context: Context,         // 对话上下文（系统提示 + 消息 + 工具）
#   options?: TOptions,       // 可选配置（思考级别、缓存等）
# ) => AssistantMessageEventStream;  // ← 必须返回统一事件流
# ============================================================
# 教学示意：异步流函数的类型契约；非官方 Python SDK。
from collections.abc import AsyncIterator
from typing import Protocol

class StreamFunction(Protocol):
    def __call__(
        self,
        model: Model,
        context: Context,
        options: StreamOptions | None = None,
    ) -> AsyncIterator[AssistantMessageEvent]:
        raise NotImplementedError
```

这个签名定义了三条规则：

1. **输入相同**：所有翻译器接受同样的三个参数（model、context、options）
2. **输出相同**：必须返回 `AssistantMessageEventStream`——不管底层是原始 SSE 还是 SDK 流，对外都是这个类型
3. **流内错误走事件协议**：流开始后的请求或解析异常通常编码为 `{ type: "error" }` 终止事件

第 3 条是流实现要遵守的**事件契约**，不是 TypeScript 自动提供的异常保护。Provider 请求失败时，适配器通常把异常包装成 `error` 事件；但部分 `streamSimple()` 会在创建流之前同步校验认证，例如 Anthropic 的 `assertRequestAuth()`。经 `Models.streamSimple()` 调用时，这类异常发生在 `lazyStream()` 的异步准备阶段，会被编码为 `error` 事件；直接调用 API 的 `streamSimple()` 则可能同步抛出异常。

编码成事件的意义是让失败能沿正常事件通道被观察到。当前 Agent Loop 遇到 `error` / `aborted` 会发送 `turn_end`、`agent_end` 并结束本次运行；宿主可以在之后的运行中另行决定是否重试。**错误进入事件流，不代表当前循环会自动继续。**

有了 StreamFunction 这套规则，"前台"（第一层）可以把工作派给不同翻译器，并通过同一种事件协议消费流内的成功与失败结果。

## 三、怎么用：从调用到接入新模型

理解了三层架构，现在看实际使用。分两个场景：**怎么调用**已有模型，和**怎么接入**一个新模型。

### 场景一：调用模型

实例入口和 API 实现都区分 `stream()`、`streamSimple()`。为什么有两个版本？

`Models.stream()` 和 `Models.streamSimple()` 都先路由、准备认证，差别在下游接受的参数：前者允许 API 专用配置，后者接受 `reasoning` 等通用配置，由各 API 的便捷包装翻译思考参数并调整 token 上限。简单说：

- **`stream()`**：使用 API 对应的选项，例如 Anthropic 的 `thinkingEnabled`、`effort` 等
- **`streamSimple()`**：使用通用选项，例如 `reasoning: "high"`，由 API 适配层做映射

沿用上一节的 `models` 与 `model`，先直接消费流，再把同一个调用入口交给 Agent：

```python
# ============================================================
# 【Python改写】消费统一事件流
# 概念对照（异步迭代收到统一事件后，按事件类型处理文本增量、工具调用、完成和错误。）
# 原文 TS（完整节选，逐行注释）：
# const context = {
#   messages: [{ role: "user" as const, content: "帮我读一下 main.ts", timestamp: Date.now() }],
# };
# const stream = models.streamSimple(model, context, { reasoning: "high" });
# //                                          ↑ 告诉它"用高级别思考"
# //                                            streamSimple 会自动翻译成各 Provider 的具体参数
#
# for await (const event of stream) {
#   // 事件会按顺序到达：
#   // start → thinking_start/delta/end → text_start/delta/end → done
#   switch (event.type) {
#     case "text_delta":
#       // 文字增量，显示到终端
#       break;
#     case "toolcall_end":
#       // 模型要调工具，拿到完整的工具调用信息
#       break;
#     case "done":
#       // event.message 是终态；deferred 时结果还未完成
#       break;
#     case "error":
#       // event.reason 是 "error" 或 "aborted"，event.error 是终态消息
#       break;
#   }
# }
# ============================================================
async def consume_stream():
    # 教学示意：消费异步事件流，再将同一个调用入口交给 Agent；非官方 Python SDK。
    context = {
        "messages": [{"role": "user", "content": "帮我读一下 main.ts", "timestamp": now_ms()}]
    }
    stream = models.stream_simple(model, context, {"reasoning": "high"})

    async for event in stream:
        event_type = event["type"]
        if event_type == "text_delta":
            pass  # 将文字增量显示到终端
        elif event_type == "toolcall_end":
            pass  # 取得完整工具调用信息
        elif event_type == "done":
            pass  # deferred 时终态结果可能尚未完成
        elif event_type == "error":
            pass  # 区分 error 与 aborted
```

**Agent Loop 不需要关心底层是哪个模型。** 不管 model 是 Claude、GPT 还是 Gemini，`streamSimple` 返回的都是同一种事件流，消费方式完全一样。

```python
# ============================================================
# 【Python改写】把模型流接入 Agent
# 概念对照（Agent 接收模型和流函数，Loop 因而不必知道 Provider 的协议细节。）
# 原文 TS（完整节选，逐行注释）：
# import { Agent } from "@earendil-works/pi-agent-core";
#
# const agent = new Agent({
#   initialState: { model, systemPrompt: "你是一个助手。" },
#   streamFn: models.streamSimple.bind(models),
# });
# ============================================================
# 教学示意：把统一流函数交给 Agent；非官方 Python SDK。
agent = Agent(
    initial_state={"model": model, "system_prompt": "你是一个助手。"},
    stream_fn=models.stream_simple,
)
```

上面的直接调用只有一条 user 消息，没有注册 `read` 工具，所以它只是展示调用与消费方式，不会真的读取 `main.ts`。到了工具章节，我们再把工具 schema 和执行函数接进来。

### 场景二：接入一个新模型

假设你要接入一个 Pi 还不支持的新模型——比如某个国产大模型。你要做什么？

**三步**，每步对应前面讲的三层架构：

**第 1 步：先判断是否需要写翻译器**（对应第三层）

如果新模型兼容已有协议，优先复用对应 API；只有请求和响应格式无法由现有 API 覆盖时，才实现自己的 `ProviderStreams`。自定义实现要做的是：

- 把 Pi 的统一消息格式，翻译成你的模型的 API 格式（请求方向）
- 把你的模型返回的流式响应，翻译成 Pi 的 12 种统一事件（响应方向）
- 把请求或响应解析异常转换为终止的 `error` 事件；创建流之前的认证校验等异常仍可能同步抛出

这一步是工作量最大的——你需要读模型的 API 文档，搞清楚它的消息格式、流式协议和错误码。把这些协议差异集中在 Provider API 实现中，后续配置模型时就可以复用；如果服务端协议或认证规则变化，仍需相应调整。

**第 2 步：创建 Provider 并配置模型**（对应第一层）

```python

# 【Python改写】创建自定义 Provider 和模型
# 概念对照（提供商描述模型元数据、认证和 API 实现；模型由集合注册后供调用。下面的 Python 字典只对应结构。）
# 原文 TS（完整节选，逐行注释）：
```

这里复用了 OpenAI Completions 实现，因此不需要另写 `stream` 或 `streamSimple`。`createProvider()` 要求显式提供 `auth`、模型列表和 API 实现；若认证不是 API Key，可按 Provider 的认证机制提供相应的 `auth` 定义。`Models` 先按 `model.provider` 定位并准备认证，再由 Provider 按 `model.api` 选择实现。若模型不是 OpenAI Chat Completions 兼容协议，就把自定义 API 实现传给 `createProvider()`。

**第 3 步：取出模型并交给 Agent**（连接到调用入口）

```python
# ============================================================
# 【Python改写】取出模型并交给 Agent
# 概念对照（集合根据 Provider 和模型 id 取回模型，再把统一流函数交给 Agent。）
# 原文 TS（完整节选，逐行注释）：
# import { Agent } from "@earendil-works/pi-agent-core";
#
# const model = models.getModel("your-provider", yourModel.id);
# if (!model) throw new Error("Model not found");
#
# const agent = new Agent({
#   initialState: { model, systemPrompt: "你是一个助手。" },
#   streamFn: models.streamSimple.bind(models),
# });
#
# await agent.prompt("用一句话介绍自己。");
# ============================================================
async def main():
    # 教学示意：连接已注册的模型与 Agent；非官方 Python SDK。
    model = models.get_model("your-provider", your_model["id"])
    if model is None:
        raise LookupError("Model not found")
    agent = Agent(
        initial_state={"model": model, "system_prompt": "你是一个助手。"},
        stream_fn=models.stream_simple,
    )
    await agent.prompt("用一句话介绍自己。")
```

Agent Loop 的调用代码保持不变。兼容已有协议时，主要工作是描述模型、Provider、认证和地址；只有协议无法复用时，才需要实现翻译器。

## 四、【进阶】翻译器内部：SSE 解析与思考模式方言

> 前三节覆盖了 AI 抽象层的核心设计。以下内容属于工程实现细节——如果你不需要自己写翻译器，可以跳过这一节。

### 流式传输：为什么 Anthropic 和 OpenAI 的解析方式完全不同？

第 3 章讲过，模型回复是流式的——一个字一个字"吐"出来。但"怎么吐"各家不同：

**OpenAI** 的 SDK 提供结构化 chunk 流。Pi 调用 `client.chat.completions.create(...).withResponse()`，再读取每个 chunk 里的 `choices[0].delta`。

**Anthropic 也使用 SDK。** Pi 创建 `@anthropic-ai/sdk` 客户端，调用 `client.messages.create(...).asResponse()` 取得原始 HTTP `Response`；随后由 Pi 自己读取 `response.body`，逐行解析 SSE 的 `event:` 和 `data:`，再修复并解析事件 JSON。

```
Anthropic 的解析链路（SDK 发请求，Pi 解析 SSE）：
  SDK messages.create(...).asResponse() → Response.body → 逐行读取 → 分离 event 和 data → JSON 解析(含容错) → Pi 事件

OpenAI Completions 的解析链路（SDK 返回结构化 chunk）：
  client.chat.completions.create(...).withResponse() → AsyncIterable<Chunk> → Pi 映射成统一事件
```

差别在于 SDK 暴露给 Pi 的响应边界：Anthropic 使用 SDK 的响应对象，Pi 再解析原始 SSE；OpenAI SDK 则直接提供结构化流。两条路径最终都由 API 适配器映射为统一事件。

### 思考模式：各家参数方言

不同 Provider 对"让模型深度思考"这件事，概念和参数完全不同：

```python
# ============================================================
# 【Python改写】映射不同 Provider 的思考参数
# 概念对照（统一的思考选项最终映射成不同 Provider API 的参数结构。）
# 原文 TS（完整节选，逐行注释）：
# // Anthropic：给一个 token 预算，让模型在这个预算内思考
# params.thinking = { type: "enabled", budget_tokens: 16384 };
#
# // OpenAI：给一个努力程度（low/medium/high）
# params.reasoning_effort = "high";
#
# // Google：用 thinkingConfig 配置
# config.thinkingConfig = { includeThoughts: true, thinkingLevel: "high" };
# ============================================================
# 教学示意：不同协议有各自的思考参数。
anthropic_params["thinking"] = {"type": "enabled", "budget_tokens": 16_384}
openai_params["reasoning_effort"] = "high"
google_config["thinkingConfig"] = {"includeThoughts": True, "thinkingLevel": "high"}
```

甚至 Anthropic 自己都有两种模式——新版模型用"自适应思考"（模型自己决定思考多少），旧版模型用"预算思考"（给固定 token 上限）。

### Pi 怎么统一：ThinkingLevel 七档刻度

Pi 定义了 `ThinkingLevel` 六个思考级别，再加上 `ModelThinkingLevel` 的关闭档 `off`，共七档：

<Diagram file="/assets/260702-ch04-thinking-levels.svg" caption="ThinkingLevel 七档思考刻度" id="260702-ch04-thinking-levels" />

**配图说明**：顶部数轴展示 off、minimal、low、medium、high、xhigh、max 七档。仅标注 token 预算 API 的四个默认预算；下方对比三家 API 对 high 的映射；底部展示 clamp 策略。

```
  off    minimal    low    medium    high    xhigh    max
  │        │         │       │        │        │       │
  关闭    1024      2048     8192     16384      各 API 按模型能力映射
```

上层代码只需说 `reasoning: "high"`，API 适配器再把它翻译成该接口的具体参数。`thinkingLevelMap` 是可选的模型映射表：缺省项交给 API 使用自己的默认映射，值为 `null` 的档位表示不支持；`xhigh` 和 `max` 只有显式映射后才会列为可用档位。

token 预算 API 的默认预算只为 `minimal`、`low`、`medium`、`high` 分别配置 1024、2048、8192、16384；调用方可以覆盖。它们不是所有 Provider 或模型共用的预算，`xhigh` / `max` 也不代表固定 token 数。各 API 会按自身协议映射思考级别，并结合可用输出空间调整预算。

如果请求的档位模型不支持（比如请求 `xhigh` 但只支持到 `high`），`clampThinkingLevel()` 会**先向上找可用档位，找不到再向下找**。

`streamSimple()` 就是帮你自动完成这套翻译的便捷函数——查表 + clamp + 调整 maxTokens，然后调用底层 `stream()`。

## 五、【进阶】缓存控制与错误处理

### 缓存控制：让模型"算更少"

Agent 对话是"有状态的"——每轮都把之前的完整历史发给模型。如果你和 Agent 聊了 50 轮，每轮都重新计算前 49 轮的内容。缓存就是告诉模型服务器："这些内容没变，别重新算了。"

但"怎么标记"各 Provider 不同：Anthropic 在消息块上追加 `cache_control` 标记，Bedrock 插入独立的 `cachePoint` 节点。

Pi 把缓存控制抽象成三个语义级别：

```python
# ============================================================
# 【Python改写】缓存保留级别
# 概念对照（Literal 将可选保留级别限制为三个语义值。）
# 原文 TS（完整节选，逐行注释）：
# type CacheRetention = "none" | "short" | "long";
# ============================================================
# 教学示意：用 Literal 表达缓存保留策略。
from typing import Literal

CacheRetention = Literal["none", "short", "long"]
```

上层只说"我要 long 缓存"，API 适配器再按自己的能力配置标记。这里不是所有实现都一定支持同一种缓存方式：

| API | `none` | `short` | `long` | 条件与打点位置 |
|-----|--------|---------|--------|----------------|
| **Anthropic Messages** | 不添加显式标记 | 添加 `cache_control: { type: "ephemeral" }` | 仅当 `supportsLongCacheRetention` 为真时加 `ttl: "1h"`，否则沿用短期设置 | system prompt；工具定义仅在 `supportsCacheControlOnTools` 为真时标记最后一个工具；仅当最终对话消息的 role 为 `user` 时标记其最后内容块 |
| **Bedrock Converse** | 不插入节点 | 仅当 `supportsPromptCaching()` 判定模型支持时插入 `cachePoint` | 同样要求模型支持；可附加 `ttl: ONE_HOUR` | system prompt 后；仅当最后一条消息 role 为 `USER` 时，在该消息内容后插入节点 |
| **OpenAI Responses** | 不发送 cache key；具备 `supportsExplicitPromptCacheMode` 时会请求显式模式 | 有 `sessionId` 时发送经过长度限制的 `prompt_cache_key` | `supportsLongCacheRetention` 为真时才加 `prompt_cache_retention: "24h"` | 不在消息中打点，key 由 sessionId 派生 |
| **OpenAI Completions 兼容接口** | 不加 Anthropic 风格标记 | 仅在解析后的 `cacheControlFormat === "anthropic"` 时加 `cache_control` | 还需 `supportsLongCacheRetention` 才加 `ttl: "1h"` | system/developer 指令、最后一个工具、从后往前找到的最后一条 user/assistant/tool 对话消息 |

这张表描述请求如何序列化，不保证服务端一定命中缓存。`none` 也不一定能关闭服务端隐式缓存：Responses API 只有在接口声明支持 `supportsExplicitPromptCacheMode` 时才会发送显式模式选项。缓存资格、命中和计费由具体模型及服务端行为决定，不能从 Pi 的保留级别推出固定节省比例。

这里有个值得停下来想一下的对比：同样是"告诉服务器这段内容不变"，四家给出了**四种完全不同的协议设计**——

- **Anthropic 的做法像"贴便签"**：在满足条件的系统提示、工具定义或对话内容块上附加 `cache_control`。
- **Bedrock 的做法像"插路标"**：在受支持模型的 system prompt 后、以及最终消息为 USER 时插入 `cachePoint`。
- **OpenAI Responses 的做法像"按会话找记录"**：在缓存启用且有 `sessionId` 时发送受长度限制的 `prompt_cache_key`；长期保留还需模型能力支持。
- **OpenAI Completions 兼容接口**：只有兼容配置选择了 Anthropic 格式时，才复用 Anthropic 风格的 `cache_control` 标记；这不代表所有 OpenAI 兼容供应商都支持它。

若多轮请求希望复用同一会话缓存，需要按对应 API 的约定稳定传入 `sessionId` 或保持前缀内容一致；各接口的标记条件不同，消息角色或模型能力不满足时，部分标记会被省略。

### 错误处理：流事件与同步异常的边界

API 的流式请求通常会把请求或解析阶段的异常编码为终止事件。下面是模式节选：前面的解析逻辑已经把成功结束原因映射为 `stop`、`length`、`toolUse` 或 `deferred`；异常和成功两条终止路径都要结束流。

```python
# ============================================================
# 【Python改写】把流异常编码为终止事件
# 概念对照（流适配器把成功结束映射为 done，把异常编码成 error 或 aborted 终止事件，并关闭事件流。）
# 原文 TS（完整节选，逐行注释）：
# try {
#   // ... 正常流程：构建请求、发送、解析响应
#   if (
#     output.stopReason === "pending" ||
#     output.stopReason === "error" ||
#     output.stopReason === "aborted"
#   ) {
#     throw new Error("Stream ended without a successful stop reason");
#   }
#   stream.push({ type: "done", reason: output.stopReason, message: output });
#   stream.end();
# } catch (error) {
#   // 错误不抛出，而是编码到流中
#   const reason = options?.signal?.aborted ? "aborted" : "error";
#   output.stopReason = reason;
#   output.errorMessage = error instanceof Error ? error.message : String(error);
#   stream.push({ type: "error", reason, error: output });
#   stream.end();
# }
# ============================================================
# 教学示意：成功与异常都通过终止事件结束流；非官方 Python SDK。
try:
    if output["stop_reason"] in {"pending", "error", "aborted"}:
        raise RuntimeError("Stream ended without a successful stop reason")
    stream.push({"type": "done", "reason": output["stop_reason"], "message": output})
    stream.end()
except Exception as error:
    signal = options.get("signal") if options else None
    reason = "aborted" if signal is not None and signal.is_set() else "error"
    output["stop_reason"] = reason
    output["error_message"] = str(error)
    stream.push({"type": "error", "reason": reason, "error": output})
    stream.end()
```

这里的 `stopReason: "error"` 和 `"aborted"` 是适配器在异常时设置的统一状态。经 `Models.streamSimple()` 调用时，认证解析和 API 初始化也包在 `lazyStream()` 的异步准备中；准备阶段失败同样会成为 `error` 事件。直接调用部分 API 的 `streamSimple()` 时，认证断言（如 Anthropic 的 `assertRequestAuth()`）可能在返回流之前同步抛出异常。

Agent Loop 收到 `error` / `aborted` 后会结束当前运行并发送 `turn_end`、`agent_end`；宿主可在后续运行中选择重试或报告错误。事件协议本身不会让当前循环自动重试。

还有一个隐蔽的问题：**上下文溢出**。`isContextOverflow()` 有三种判定：

1. `stopReason === "error"`，且 `errorMessage` 命中溢出模式、没有命中已知的非溢出模式。
2. 提供了 `contextWindow`、`stopReason === "stop"`，并且 `usage.input + usage.cacheRead > contextWindow`。
3. 提供了 `contextWindow`、`stopReason === "length"`、`usage.output === 0`，并且 `usage.input + usage.cacheRead >= contextWindow * 0.99`。

后两种是按用量识别服务端静默溢出或截断输入；没有 `contextWindow` 时，这两种用量判定不会运行。

## 六、回到那一行代码

回到开头的问题：`streamSimple(model, context)` 这一行代码背后发生了什么？

用一句话概括：**Agent Loop 调用 `Models.streamSimple()` 后立刻拿到事件流；Models 按 `model.provider` 找 Provider、准备认证，再由 Provider 按 `model.api` 选择 API 实现，最后把模型响应映射为统一事件——Agent Loop 只消费这个事件流。**

```
Agent Loop：models.streamSimple(model, context, { reasoning: "high" })
    │
    │  ① Models 立即返回 AssistantMessageEventStream（外层 lazyStream）
    │
    │  ② 异步准备：requireProvider(model.provider) → applyAuth(...)
    │
    │  ③ provider.streamSimple(...)
    │      → createProvider 按 model.api 选择 API 实现
    │      → API streamSimple 映射思考选项，再调用 API stream
    │
    │  ④ API 发请求并把响应映射为 12 种统一事件
    │
    └── Agent Loop：for await (event of stream) { ... }  ← 消费事件流
```

**Agent Loop 看到的只有 ④ ——一个干净的事件流。** 这就是三层架构的力量：复杂度被封装在翻译器里，外部接口保持简洁。

### 设计精华

三条核心思路值得带走：

**1. "协议 > 实现"设计法。** Pi 没有设计一个 `BaseProvider` 抽象类让所有翻译器继承，而是定义了一套事件协议（12 种事件）和一个函数签名（`StreamFunction`）。为什么不用继承？因为翻译器之间几乎没有共同点——继承需要找共同代码，但 Anthropic 和 Google 在"发消息"这件事上连字段名都不一样。协议只约定"输入什么、输出什么"，不管中间怎么处理。

**2. "统一枚举 + 可选映射"策略。** `ThinkingLevel` 提供六个通用档位，`ModelThinkingLevel` 再加 `off`。可选的 `thinkingLevelMap` 允许模型覆盖映射或标记不支持的档位；各 API 仍负责把档位翻译成自己的参数。

**3. "语义统一，实现分散"。** `cacheRetention`（none/short/long）是语义接口——上层说"我要长期缓存"，不管底层是打标记还是插节点。语义接口描述"做什么"，机制接口描述"怎么做"。
